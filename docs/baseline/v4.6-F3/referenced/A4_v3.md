## 5. Final Interest Model and State Machine

The structure is **[TR]**. Behaviours marked **(REC-BIZ, OD-06x)** are unapproved.

**`Interest`**
- `id` (UUID), `sender_profile` (PROTECT), `receiver_profile` (PROTECT)
- `status`: `PENDING | RECIPROCATED | CONVERTED_TO_REQUEST | DECLINED | WITHDRAWN | EXPIRED | CLOSED`
- `sent_at`, `responded_at`, `expires_at` (nullable), `closed_at`, `closure_reason` (`BLOCKED | PROFILE_CLOSED | ACCOUNT_DELETED | SUPERSEDED_BY_REQUEST`)
- `created_by`, `updated_by` (actual accounts)

**Constraints:** `CHECK sender <> receiver`. Partial unique on `(LEAST, GREATEST)` of the pair `WHERE status IN ('PENDING','RECIPROCATED')`.

**Canonical link:** `MatrimonialRequest.source_interest`: OneToOne, nullable, PROTECT, `related_name="formal_request"`. **There's no FK from Interest to the request.** It's written once, in the transaction that creates the request, and the OneToOne makes it impossible for one interest to produce two requests.

**`InterestHistory`** (append-only) and **`DirectionalCooldown`** (`source_type` INTEREST|REQUEST, `source_id` unique, `reason`, `starts_at`, `ends_at`): unchanged from v2.

| From | Event | Actor | To | Notes |
|---|---|---|---|---|
| — | Express interest | Sender (`send_interests`) | PENDING | |
| — | Express interest while the reverse interest is PENDING | Sender | Reverse row → RECIPROCATED, no new row | (REC-BIZ, OD-06a) |
| PENDING | Show interest back | Receiver | RECIPROCATED | |
| PENDING | Send formal request | Receiver | CONVERTED_TO_REQUEST | Request receiver→sender. The receiver's owning account pays. [Recipient option DECIDED; payer follows formal-request rules] |
| PENDING | Send formal request | Original sender | CONVERTED_TO_REQUEST | (REC-BIZ, OD-06b) |
| RECIPROCATED | Send formal request | Either party | CONVERTED_TO_REQUEST | Initiator's owning account pays (REC-BIZ, OD-06c) |
| PENDING | Decline | Receiver | DECLINED | **30-day cooldown sender→receiver [DECIDED]** |
| PENDING | Withdraw | Sender | WITHDRAWN | No cooldown (REC-BIZ, OD-06d) |
| PENDING | Expiry job | System | EXPIRED | Only if OD-06e is approved. No cooldown. |
| PENDING/RECIPROCATED | Block (either direction), profile CLOSED, deletion PROCESSING | System | CLOSED | The counterparty sees "No longer pending" (REC-BIZ, OD-06f) |
| PENDING/RECIPROCATED | Profile PAUSED or SUSPENDED | — | Unchanged (frozen) | (REC-BIZ, OD-06f) |
| PENDING/RECIPROCATED | Hide (either direction) | — | **Unchanged** | [DECIDED: hiding prevents only new approaches] |

**Interactions with formal requests:**
1. **Creating an interest** is rejected generically if the pair has a PENDING request in either direction, a connection, or an active cooldown in that direction.
2. **Creating a request** while the pair has a live interest converts and links that interest in the same transaction [TR].
3. A converted request that is DECLINED or EXPIRED triggers the request cooldown [DECIDED].
4. **Cross-effect of cooldowns:** an active cooldown in one direction blocks both interests and requests in that direction (REC-BIZ, OD-06g). The reverse direction is never affected [DECIDED].

**Concurrency [TR]:** pair advisory lock → interest row lock. The partial unique index is the backstop.

**Tests (T-INT-001…020):** every transition and actor, the canonical-FK uniqueness, concurrent conversion charging exactly once, cooldown direction, freeze vs. close, and manager permission denial.

## 8. Authentication Lifecycle [TR-01]

### 8.1 Records (no migration yet)
- **`AuthSession`:** `id`, `user`, `client_type` (WEB|MOBILE), `status` (ACTIVE|REVOKED|EXPIRED), `created_at`, `last_seen_at`, `idle_expires_at`, `absolute_expires_at`, `reauthenticated_at`, `revoked_at`, `revoked_reason`, device and network metadata (`device_name`, `platform`, `app_version`, `user_agent`, `login_ip`, `last_ip`, `approximate_location`).
- **`AuthToken`** (mobile): `session`, `token_type` (ACCESS|REFRESH), `token_hash` (unique), `generation`, `parent_id` (the refresh token it replaced), `key_version`, `issued_at`, `expires_at`, `used_at`, `revoked_at`.

### 8.2 Linking a web session to AuthSession, without storing raw session keys
1. Use Django's server-side session store (database, or cache_db backed by Redis). The browser cookie holds only Django's random session key.
2. At login, Django `login()` rotates the key (preventing fixation). The server then writes `request.session["auth_session_id"] = <AuthSession UUID>` **inside the server-side session data**.
3. **`AuthSession` stores no Django session key and no hash of one.** The link runs one way: session data → `AuthSession`. Clients can't tamper with server-side session data.
4. On every request: load `auth_session_id` from the session, fetch the `AuthSession`, and require `status == ACTIVE`, `user_id == request.user.id`, and that the idle and absolute limits haven't passed. If any check fails, flush the session and return `401 session_revoked`.
5. Revocation only flips `AuthSession.status`. The orphaned Django session row is rejected on its next use and purged by the scheduled `clearsessions` job.
6. Defence in depth: Django's session auth hash also invalidates web sessions automatically when the password changes.

### 8.3 Mobile tokens and rotation
- **Token values:** 256-bit random, prefixed `mat_at_` / `mat_rt_`. Only the SHA-256 hash is stored, and plaintext is never logged.
- **Access tokens are independent of rotation.** An access token is valid when it's unexpired (15 min), unrevoked, and its **session is ACTIVE**. Rotating the refresh token **doesn't revoke the current access token**, so in-flight API calls keep working until the token expires naturally. Logout, revocation and reuse detection still take effect immediately, because every request checks the session status.
- **Deterministic, idempotent rotation:**
  - The child refresh token is derived as `HMAC-SHA256(K_rot[key_version], parent_plaintext ‖ "refresh" ‖ generation+1)`.
  - The new access token is derived the same way with the label `"access"`.
  - The server stores only the children's hashes. It can **recompute the same pair** from the parent token the client presents again, **without ever storing plaintext tokens**.
- **`POST /auth/token/refresh/`**, all in one transaction with `SELECT … FOR UPDATE` on the parent row:

| Parent state | Result |
|---|---|
| Valid and unused | Mark `used_at`. Insert the child hashes. Extend the rolling expiry, capped at the 90-day absolute limit. Return the pair. |
| Used ≤ 15 s ago and **child refresh not yet used** | **Recompute and return the identical pair** (idempotent replay). Nothing new is created. |
| Used > 15 s ago, **or** its child has already been used | **Reuse detected:** revoke the session (REFRESH_REUSE), record a security event, send a security notification. `401 session_revoked`. |
| Expired or session not ACTIVE | `401 session_expired` |
| Unknown | `401 invalid_token` |

**How the 15-second grace works, and how the client recovers:**
1. The mobile client runs refresh as **single-flight**: one refresh at a time, and every request that got a 401 waits for it.
2. The client keeps the old refresh token until the new pair is safely stored.
3. If the refresh response is lost (timeout or dropped connection), the client retries **with the same old token** for up to 10 seconds. Inside the grace window, the server recomputes and returns the identical pair.
4. Two concurrent refreshes also receive the same pair. The row lock serialises them, and no extra generation is created.
5. If the client stays offline past the grace window, its next attempt counts as reuse. The session is revoked and the user logs in again. That's the deliberate security trade-off.
6. A thief replaying a stolen token inside the grace window gets the same pair as the real user. Whichever side uses the child refresh token second triggers reuse detection, and the session is revoked.
7. **The key `K_rot` is versioned and stored in the deployment secret store**, and rotating it doesn't invalidate existing tokens (the `key_version` column records which key derived each token).

## 9. Acting-Profile Authorization Algorithm [TR-02]

**Principle:** `X-Acting-Profile` *selects* a context. It never proves authorization.

**Ordered steps** (every profile-scoped request):
1. **Authenticate the account** per §8, including the account-state gate. The result is `actual_account`.
2. **Classify the endpoint.** Account-scoped endpoints reject the header with `400 header_not_allowed`. Profile-scoped endpoints continue to step 3.
3. **Select the profile.** Use the header (must be a valid UUID, otherwise `400`). If there's no header, use the caller's own personal profile. If there's neither, return `400 acting_profile_required`.
4. **Load the selected profile.** It must exist, not be CLOSED, and not have its owner's deletion in PROCESSING. Otherwise return `404 acting_profile_not_available`. The same response covers every failure in steps 4–7.
5. **Ownership:** if `profile.owner_id == actual_account.id`, mark the caller as owner and go to step 8.
6. **Manager authorization:** a `ProfileManagerAuthorization(profile, manager=actual_account)` row must exist with `status == ACTIVE`. PAUSED, PENDING, REVOKED, EXPIRED and REJECTED all deny, so **a paused manager has no access at all** [DECIDED]. Otherwise 404.
7. **Authorization expiry:** `expires_at IS NULL OR expires_at > now()`, evaluated at runtime regardless of the job-maintained status. Otherwise 404.
8. **Owner account status:** the owner account must be active, not deactivated, without a `FULL_ACCOUNT` restriction, and not in the deletion recovery period or processing (new activity is disabled then). For managers this returns `403 acting_profile_unavailable`; for owners, step 1 already covers it.
9. **Required permission:** each endpoint declares a permission code and tier.
   - Owners hold all owner capabilities.
   - For managers, an O-tier action returns `403 permission_not_granted`. Otherwise the `AuthorizationPermission` row must have `is_granted=True` and the catalogue entry must be active; if not, `403 permission_not_granted`.
10. **Step-up verification:**
    - S (communication): `AuthSession.reauthenticated_at` within 12 h.
    - Other S: within 10 min.
    - H: a valid, unconsumed `SensitiveActionVerification` for this exact action, consumed atomically in the business transaction, plus owner approval where required.
    - Owner O-tier actions (export, deletion, security changes): owner step-up within 10 min.
    
    If any check fails: `403 step_up_required`.
11. **Resource participation:** any resource in the path is loaded **through a query filtered by the represented profile** (for example, a request where sender or receiver is that profile, a conversation where it's a participant, a document it owns or holds an active permission for).
    - If not found: `404`, identical to a non-existent resource.
    - A participant acting in the wrong role (for example, the sender trying to accept): `403 action_not_allowed`.
12. **Eligibility and state:** block, hide, restriction and connection-state checks through the eligibility service. Failures return generic errors that reveal no hidden relationship.
13. **Transactional re-verification (writes):** inside the service transaction, `SELECT … FOR SHARE` on the authorization row and re-check steps 6–7. Pause and revoke take `FOR UPDATE`.
14. **Billing account:** `billing_account = represented_profile.owner`. **It's never `actual_account` unless the caller is the owner.**
15. **Build the immutable `ActorContext`:** `actual_account`, `represented_profile`, `is_owner`, `authorization_id`, `permission_code`, `step_up_reference`, `billing_account`, `request_id`, `ip`, `user_agent`. It's per-request only and never cached.
16. **Execute the service.** Services accept an `ActorContext`, never raw actor or profile IDs from the client.
17. **Record:**
    - domain history (`performed_by` = actual account, `performed_for_profile` = represented profile)
    - audit (`actor_type` OWNER|MANAGER, `authorization_id`, `request_id`)
    - `ManagerActionLog` and `ProfileAccessHistory` on the manager path
    - owner notification via the outbox for S and H actions
    
    The response uses context-aware field allowlists.

## 10. Profile-View Billing Workflow [DECIDED rules; TR-08 mechanics]

**Billing account** = the owner account of the represented profile performing the view. **A manager's personal account is never charged, read or locked for a delegated view.** The window is a rolling 24 hours per (billing account, target) [DECIDED]. Allowance is consumed before purchased credits [DECIDED].

**Billing is separate from visibility:** the access level (L0–L3, OD-03) decides *whether* full detail can be seen at all. Billing decides only whether a view grant must be paid for. Billing never widens access.

**`POST /profiles/{id}/views/`**, in one transaction:
1. Run §9 with `view_profile_details`. Eligibility must allow L2.
2. Apply the exemptions if OD-08a is approved. Until then, no exemptions are implemented.
3. `SELECT … FOR UPDATE` on the billing account's `CreditWallet`. This is the per-account serialisation point for the owner and all their managers.
4. Look for a billable view by this billing account for this target within the last 24 hours. If one exists, record a non-billable view and return the existing grant.
5. Otherwise lock the active PROFILE_VIEW allowances (earliest expiry first) and debit 1, falling back to the purchased view bucket. If both are empty, raise `insufficient_profile_view_credits` and roll everything back (response per OD-08b).
6. Insert the ledger row with `bucket_balance_after`, update the projection, write `ProfileView` (with `billing_account`, `viewer_user`, `viewer_profile`), write `VisitorHistory` (respecting private browsing), write the audit entry.
7. Commit.

**`GET /profiles/{id}/`** returns full detail only when a grant exists in the window, or an approved exemption applies. Otherwise `402 profile_view_required`. The `GET` itself never charges.

**Guarantees:**
- **Idempotency:** the optional `Idempotency-Key` header replays the original response. Even without it, the window rule under the wallet lock prevents double charging.
- **Rollback:** any failure leaves no ledger row, projection change or view record. If the response fails after commit, the grant already exists, so a retry costs nothing.
- **Ledger consistency:** governed by §6 rows 8–9.

**Tests:** T-MAT-010…016 (from v2), plus T-MAT-017: GET never charges, and T-MAT-018: billing never grants access above the visibility level.
