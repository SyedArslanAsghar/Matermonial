### 1.1 Three independent status dimensions [TR]

| Dimension | Applies to | Values |
|---|---|---|

**Rules:**
- The dimensions are independent. An APPROVED requirement can be NOT_STARTED. An IMPLEMENTED feature can belong to a PROPOSED requirement, but then it can't progress beyond TESTED until the requirement is approved.
- `CLAUDE.md` §19 currently uses `APPROVED` as an *implementation* status. I propose renaming it to **`ACCEPTED`** (owner accepted the implementation) so it doesn't collide with requirement approval. That's a wording change to `CLAUDE.md` and needs your approval (DCR-12).
- `POST_MVP` moves to the requirement dimension because it describes scope, not progress.

### 1.2 Authentication lifecycle specification [TR, needs sign-off as security architecture]

**Records.** No migration yet. These are the proposed models.
- `AuthSession`: `id`, `user`, `client_type` (WEB|MOBILE), `status` (ACTIVE|REVOKED|EXPIRED), `created_at`, `last_seen_at`, `idle_expires_at`, `absolute_expires_at`, `reauthenticated_at`, `revoked_at`, `revoked_reason` (LOGOUT, USER_REVOKED, PASSWORD_RESET, PASSWORD_CHANGED, DEACTIVATED, ADMIN, REFRESH_REUSE, ACCOUNT_DELETION, SECURITY), `device_name`, `platform`, `app_version`, `user_agent`, `login_ip`, `last_ip`, `approximate_location` (city level, nullable).
- `AuthToken` (mobile only): `session`, `token_type` (ACCESS|REFRESH), `token_hash` (unique, SHA-256), `generation`, `issued_at`, `expires_at`, `used_at`, `revoked_at`.
- Tokens are 256-bit random values with the prefixes `mat_at_` and `mat_rt_` (so secret scanners can detect them). **Plaintext is never stored or logged.**
- **Change:** `AuthSession` supersedes doc 03's `LoginHistory` (DCR-25). Failed attempts go to `AccountSecurityEvent`.

**Default lifetimes** (all configurable):

| Item | Default |
|---|---|
| Web session | 7-day idle, 30-day absolute |
| Mobile access token | 15 minutes |
| Mobile refresh token | 30-day rolling, 90-day absolute (session cap) |
| Step-up (re-authentication) validity | 10 minutes |
| Refresh-reuse grace | 15 seconds |

| Lifecycle event | Specification |
|---|---|
| **Login** `POST /auth/login/` | Phone + password + `client_type` + device metadata. The response is the same generic `invalid_credentials` whether the account exists or not, and a dummy password hash runs for unknown phones so timing doesn't reveal existence. The account-state gate (below) runs first. On success the system: creates an `AuthSession`; **for web**, calls Django `login()` (which rotates the session key, preventing fixation) and links the session; **for mobile**, issues an access + refresh pair; records a security event and an audit entry; and emits an outbox event for the security notice "new sign-in". Phone-unverified accounts may log in with only the capabilities needed to verify. |
| **Per-request authentication** | **Web:** the Django session resolves to its `AuthSession`, which must be ACTIVE and within its idle and absolute limits. `last_seen_at` is updated at most every 5 minutes. **Mobile:** the bearer hash resolves to an `AuthToken` (ACCESS, unexpired, unrevoked) and then its session (ACTIVE). **Both:** the account-state gate runs on every request. A request carrying both a cookie session and a bearer token is rejected. |
| **Account-state gate** | Rejects the request if `is_active` is false, there's an active `LOGIN`/`FULL_ACCOUNT` restriction, or deletion is in PROCESSING. During the deletion recovery period, login is allowed with limited capabilities so the user can cancel. |
| **Access-token expiry** | `401` with code `token_expired`, distinct from `invalid_token`. The client refreshes once and retries. |
| **Refresh rotation** `POST /auth/token/refresh/` | One transaction: `SELECT … FOR UPDATE` on the token row. If it's valid and unused, mark `used_at`, issue the next refresh (generation + 1) and a new access token, revoke the session's previous access token, and extend the rolling expiry without passing the absolute cap. |
| **Refresh reuse detection** | If a refresh token is presented again after use: within the 15-second grace it returns `401 refresh_superseded` with no revocation (this covers a lost response on a flaky network); after the grace it **revokes the whole session (REFRESH_REUSE)**, records a security event and sends the user a security notification. The row lock means two concurrent refreshes can never both succeed. |
| **Logout** `POST /auth/logout/` | Revokes the current session (web: Django session flushed; mobile: every token of the session). Idempotent. |
| **Session list and revocation** | `GET /auth/sessions/` shows device, platform, coarse location, masked IP, created and last-seen times, and a "current" flag. Never tokens. `DELETE /auth/sessions/{id}/` returns an identical `404` for sessions that aren't the caller's. `POST /auth/sessions/revoke-others/`. Revocation takes effect on the next request because every request checks `AuthSession.status`, so no session-key lookup is needed. |
| **Password reset** | `POST /auth/password/forgot/` always returns a generic response. If the account exists and is allowed, an OTP is sent (purpose PASSWORD_RESET, documented limits). `POST /auth/password/reset/` verifies the OTP (single use, attempt-capped), applies password validators, sets the password, **revokes all sessions and tokens**, records a security event and sends a security notification. No automatic login afterwards. |
| **Password change** (authenticated) | Requires the current password + step-up. Revokes all *other* sessions; the current one is kept and rotated. |
| **Step-up** `POST /auth/reauthenticate/` | Password (+ OTP if OD-04 approves it). Sets `AuthSession.reauthenticated_at`. Sensitive endpoints require it within 10 minutes. |
| **Deactivation** | The account-state service sets `deactivated` and the reason and recomputes `is_active`, then **revokes all sessions in the same transaction**. Discovery exclusion is computed, not stored. Managers acting on that owner's profiles are denied by the acting-profile check (1.3), and the authorization rows aren't mutated. The reactivation path is a recommended default (section 9, list R). |
| **Manager authorization revocation or pause** | This is authorization, not authentication. The acting-profile context is resolved fresh from the database on every request and never cached, so it **takes effect on the next request** with no token change. Delegated writes lock the authorization row (1.3), so an in-flight write either completes before the revocation commits or is denied. Pending sensitive-action verifications for that authorization are invalidated. Already-issued photo signed URLs live at most 300 seconds; documents go through a proxy and are revoked immediately. |
| **Device and session history** | Revoked and expired sessions are retained for history under a `DataRetentionPolicy` category (period set by legal policy, OD-005). IP-to-city lookup is an external provider choice; the field stays null until one is chosen. |
| **Cookies and CSRF** | Same-origin deployment (Nginx serves the SPA and `/api/`; Vite proxies locally). Production cookie names `__Host-mat_session` (HttpOnly, Secure, SameSite=Lax, Path=/, no Domain attribute) and `__Host-mat_csrf` (readable by JavaScript, Secure, SameSite=Lax). `CSRF_TRUSTED_ORIGINS` = the app origin. DRF enforces CSRF on unsafe methods for session requests, **including login** (the SPA fetches the token from `GET /auth/csrf/`). Bearer requests are cookie-less and exempt. HSTS, `X-Frame-Options: DENY` and nosniff are already present. |
| **Rate limits** (Redis-backed in production) | Login: 5 per 15 min per phone+IP and 20 per 15 min per IP. Register: 10 per hour per IP. OTP: as documented (5 per hour per phone, 60-second resend, 5 attempts) plus a per-IP limit. Forgot-password shares the OTP budget. Refresh: 30 per hour per session. **No hard account lockout** (that would let an attacker lock users out); throttling uses back-off instead. Responses are `429` with `Retry-After` and generic text, and failures are logged as security events. |

### 1.3 Acting-profile verification [TR, needs sign-off]

**Principle:** `X-Acting-Profile` only *selects* the context. Authorization always comes from database records checked on every request.

**Endpoint classes:**
- **Account-scoped** endpoints (`/auth/*`, own notifications, export, deletion) reject the header.
- **Profile-scoped** endpoints require a resolvable acting profile. If the header is absent, the caller's own personal profile is used. If the caller has none, the request fails with `400 acting_profile_required`.

**Resolution algorithm** (`resolve_actor_context(request, required_permission)`):
1. **Actual acting account** = the authenticated user from 1.2, never taken from the request body or header.
2. Parse the header as a UUID and load the profile. If it's missing, malformed or `CLOSED`, return **`404 acting_profile_not_available`**. The same error covers unknown and unauthorized profiles, so existence isn't revealed.
3. **Ownership:** if `profile.owner_id == account.id`, the caller is the owner, and the owner holds every owner capability.
4. **Otherwise, manager path:** load `ProfileManagerAuthorization(profile, manager=account)` and require:
   - `status == ACTIVE` (PAUSED, PENDING, REVOKED, EXPIRED and REJECTED all mean no access; **a paused manager has no access at all**, including `view_profile`) [DECIDED]
   - `expires_at IS NULL OR expires_at > now()`, compared **at runtime** (the expiry job's lag doesn't matter)
   
   If either fails, return the same 404.
5. **Owner account usable:** the represented profile's owner isn't deactivated and isn't in deletion processing. Otherwise every delegated action is denied.
6. **Required permission:** each view declares `required_manager_permission`. For managers:
   - the `AuthorizationPermission(is_granted=True)` row must exist and its catalogue entry must be active
   - **Tier S** additionally needs a valid manager step-up (within 10 minutes), and then emits an owner notification and an audit entry
   - **Tier O** is always denied to managers
   
   If the check fails, return `403 permission_not_granted`. The caller has already proven they can see the profile at this point, so this doesn't leak anything.
7. **Resource consistency:** any resource addressed in the path (request, conversation, document) must involve the represented profile. Otherwise return 404.
8. **Write consistency:** for state-changing operations, the service re-reads the authorization row with `SELECT … FOR SHARE` inside the business transaction, and revoke/pause take `FOR UPDATE`. That closes the time-of-check/time-of-use gap.
9. **Output:** an immutable `ActorContext(actual_account, represented_profile, is_owner, authorization_id | None, granted_permissions, billing_account = represented_profile.owner)`. It's memoised for the request only and never shared or cached across requests.
10. **Use:** every history, audit and outbox record takes `performed_by = actual_account` and `performed_for_profile = represented_profile` from the context. Every charge uses `billing_account`.

**Tests:** T-FAM-020…035 cover: forged header to a stranger's profile → 404; paused → 404; expired by timestamp before the job runs → 404; missing permission → 403; Sensitive without step-up → 403; Owner-only → 403; revocation racing a write; billing account always the owner.

### 1.4 Profile-view billing, made explicit [TR on mechanics; billing rules DECIDED]

**Definitions:**
- **Billing account** = `represented_profile.owner`, the owner account of the profile performing the view. [DECIDED]
- **A manager's personal account is never charged** for a delegated view. Its wallet isn't even locked or read.
- **Window** = rolling 24 hours per (billing account, target profile). [DECIDED]

**API change [TR, DCR-26]:**
- `POST /profiles/{id}/views/` creates or reuses a view grant and charges if needed.
- `GET /profiles/{id}/` returns detail only if a valid grant exists for (billing account, target) within 24 hours, or an exemption applies (OD-08). Otherwise it returns `402 profile_view_required`.

Why: a `GET` that charges money can be triggered by prefetching, retries or link previews. Moving the charge to `POST` keeps `GET` safe and idempotent.

**`POST` transaction (one `transaction.atomic`):**
1. Resolve `ActorContext` with `view_profile_details`, then run the eligibility check on the target.
2. `SELECT … FOR UPDATE` on the billing account's `CreditWallet` row. This is the per-account serialisation point: concurrent views by the owner and by any of their managers queue here.
3. After the lock, look for a billable `ProfileView` for (billing_account, target) with `viewed_at > now − 24h`. If found, record a non-billable view and return the existing grant (no charge).
4. Otherwise lock the active `CreditAllowance` rows (PROFILE_VIEW, earliest `expires_at` first) and debit 1. If there's no allowance, debit purchased profile-view credits from the wallet. If there's neither, raise `insufficient_profile_view_credits`, which rolls back with nothing written.
5. Write the `CreditTransaction` (DEBIT, `bucket_balance_after`, `performed_by` = actual account, `related_profile` = target, `reference` = the ProfileView, `idempotency_key`), then the billable `ProfileView` (`billing_account`, `viewer_user`, `viewer_profile`, `target_profile`, `credit_transaction`), the `VisitorHistory` row (respecting private browsing) and the audit entry.
6. Commit. If anything fails, everything rolls back. If building the response fails after commit, the grant already exists, so a retry costs nothing.

**Idempotency:** the optional `Idempotency-Key` header is stored in `IdempotencyRecord` scoped to (billing account, endpoint). A replay returns the original response. Even without the header, the window rule plus the wallet lock prevent double charges.

**Ledger consistency:**
- Database `CHECK` constraints keep balances at zero or above.
- Every debit records `bucket_balance_after`.
- A nightly reconciliation job asserts wallet purchased balance = Σ purchased ledger entries, and allowance remaining = granted − Σ debits + Σ refunds. Mismatches raise alerts, never auto-fix, and are corrected with a compensating transaction.

**Tests:**
- T-MAT-010: search impressions never charge.
- T-MAT-011: 20 concurrent `POST`s by the owner and two managers produce exactly one charge (PostgreSQL threads).
- T-MAT-012: a manager with their own credits keeps an unchanged balance, and the owner is charged.
- T-MAT-013: the same manager viewing the same target for two different owners charges each owner once.
- T-MAT-014: a failure injected after the debit leaves no ledger row.
- T-MAT-015: the allowance is consumed before purchased credits.
- T-MAT-016: after 24 hours the view is charged again.

### 2.1 Amendments to the v1 transition additions
- **Profile PAUSED or SUSPENDED:** pending interests and requests are **frozen, not closed**. Eligibility blocks responses until the profile returns. Requests can still expire naturally.
- **Profile CLOSED or account deletion PROCESSING:** live interests become CLOSED, and pending requests become CANCELLED (system).
- **Block (either direction):** the live interest between the pair becomes CLOSED (BLOCKED), and a pending request becomes CANCELLED (system). Unblocking doesn't reopen either. Shown to the other party only as "No longer pending". These closures are REC-BIZ and part of OD-06.

## 4. Final Interest Model and State Machine

The structure is **[TR]**. Behaviours marked **REC-BIZ** await OD-06.

**`Interest`**
- `id` (UUID), `sender_profile` (PROTECT), `receiver_profile` (PROTECT)
- `status`: `PENDING | RECIPROCATED | CONVERTED_TO_REQUEST | DECLINED | WITHDRAWN | EXPIRED | CLOSED`
- `sent_at`, `responded_at`, `expires_at` (nullable, REC-BIZ), `closed_at`, `closure_reason` (`BLOCKED | PROFILE_CLOSED | ACCOUNT_DELETED | SUPERSEDED_BY_REQUEST`)
- `created_by`, `updated_by` (actual accounts), `created_at`, `updated_at`
- No free-text message field.

**Constraints:** `CHECK sender <> receiver`. Partial unique on `(LEAST, GREATEST)` of the pair `WHERE status IN ('PENDING','RECIPROCATED')`. Indexes on (receiver, status, sent_at), (sender, status, sent_at) and (status, expires_at).

**Canonical link (DCR-27):** `MatrimonialRequest.source_interest = OneToOneField(Interest, null=True, on_delete=PROTECT, related_name="formal_request")`. Interest has **no** FK back to the request. Reasons:
- Only one side owns the relationship, so there's no circular dependency or double write.
- The request is created after the interest, so the FK can be written once, in the creating transaction.
- `interest.formal_request` stays available through the reverse accessor.
- OneToOne uniqueness guarantees an interest converts at most once.

**`InterestHistory`** (append-only): `interest`, `action`, `previous_status`, `new_status`, `performed_by`, `performed_for_profile`, `reason`, `metadata`, `created_at`.

**`DirectionalCooldown`** (replaces `RequestCooldown`; schema only): `sender_profile`, `receiver_profile`, `source_type` (INTEREST|REQUEST), `source_id`, `reason` (DECLINED|EXPIRED), `starts_at`, `ends_at`. Unique (source_type, source_id). The active cooldown is `max(ends_at) > now`, so rows never need updating.

**State machine:**

| From | Event | Actor (via ActorContext) | To | Side effects |
|---|---|---|---|---|
| — | Express interest | Sender (`send_interests`) | PENDING | History, outbox `interest.received` |
| — | Express interest while the **reverse** interest is PENDING | Sender | Reverse interest → RECIPROCATED, no new row **(REC-BIZ)** | History on the existing row |
| PENDING | Show interest back | Receiver (`respond_to_interests`) | RECIPROCATED | Outbox `interest.reciprocated` |
| PENDING | Send formal request | **Receiver** (`respond_to_interests` + `send_requests`) | CONVERTED_TO_REQUEST | Request receiver→sender created with `source_interest`. Credit charged to the receiver's owning account. One transaction. |
| PENDING | Send formal request | **Original sender** (`send_requests`) | CONVERTED_TO_REQUEST **(REC-BIZ)** | Request sender→receiver, linked |
| RECIPROCATED | Send formal request | **Either party** **(REC-BIZ)** | CONVERTED_TO_REQUEST | Request from the initiator. Initiator's owning account pays. |
| PENDING | Decline | Receiver | DECLINED | **30-day cooldown sender→receiver [DECIDED]** |
| PENDING | Withdraw | Sender | WITHDRAWN | No cooldown **(REC-BIZ)** |
| PENDING | Expiry job | System | EXPIRED **(REC-BIZ, OD-06)** | No cooldown |
| PENDING/RECIPROCATED | Block (either direction), profile CLOSED, or deletion PROCESSING | System | CLOSED | No notification revealing the reason. Counterparty sees "No longer pending". |
| PENDING/RECIPROCATED | Profile PAUSED or SUSPENDED | — | Unchanged (frozen) | Eligibility blocks actions until the profile returns |
| PENDING/RECIPROCATED | Hide (either direction) | — | **Unchanged** | Hiding prevents only *new* interests [DECIDED] |

All terminal states (CONVERTED_TO_REQUEST, DECLINED, WITHDRAWN, EXPIRED, CLOSED) are final. Repeated or invalid transitions return a safe domain error and are idempotent on retry.

**Interaction with formal requests:**
1. **Creating an interest** is rejected (generically) if the pair has a PENDING request in either direction, an existing connection, or an active cooldown in that direction.
2. **Creating a formal request by any path** while the pair has a live interest: the interest is converted and linked in the same transaction. That keeps at most one live approach per pair.
3. When a converted request later becomes DECLINED or EXPIRED, the **request** cooldown applies [DECIDED]. The interest stays CONVERTED.
4. **Cross-effect of cooldowns (REC-BIZ, OD-06):** an active cooldown in one direction blocks *both* new interests and new formal requests in that direction. The reverse direction is never affected [DECIDED].

**Concurrency:** creation and conversion take `pg_advisory_xact_lock(pair_hash)` and then lock the interest row. The partial unique index is the backstop.

**Tests:** T-INT-001…020 cover each transition and its actor, auto-reciprocation, the canonical FK (at most one request per interest), concurrent conversion charging exactly once, cooldown direction, freeze vs. close, and manager permission denial.
