### B.3 Missing state transitions (additions to doc 15)

Items marked **(A)** need a BD decision.

| Entity | Added transitions / rules |
|---|---|
| **Profile** | PENDING_REVIEW→DRAFT (review rejected, or owner withdraws). SUSPENDED→ACTIVE (restriction lifted or appeal upheld, then eligibility re-checked). SUSPENDED→CLOSED (permanent action, elevated approval). DRAFT→CLOSED. Any→CLOSED (deletion processing). **Deletion recovery is modelled on account state, not profile status**, so cancelling deletion restores the profile without a transition. The meaning of PENDING_REVIEW is **(A) BD-07**. |
| **Identity verification** | NOT_SUBMITTED→PENDING_REVIEW (submit). PENDING_REVIEW→CANCELLED (user, before review). UNDER_REVIEW→PENDING_REVIEW (reviewer releases the case). UNDER_REVIEW→RESUBMISSION_REQUIRED (reviewer asks for new evidence). **Each resubmission creates a new verification cycle record.** A REJECTED cycle stays terminal and history is preserved (reconciles doc 15 §3 with FR-VER-004). |
| **Manager authorization** | PENDING→REVOKED (owner cancels invite). PENDING→EXPIRED (invitation TTL, **(A) BD-15**). PAUSED→EXPIRED (expiry reached while paused). ACTIVE/PAUSED→REVOKED (system, on owner or manager account deletion). ACTIVE/PAUSED→REVOKED by the manager resigning (**(A) BD-15**). Access checks always compare `expires_at` at runtime; the job only updates the status. |
| **Interest** | Section D |
| **Formal request** | PENDING→CANCELLED (system) on block, account deletion or profile suspension/closure, with no cooldown, consistent with "admin cancellation no cooldown". Refund handling is **(A) BD-16**. |
| **Connection** | ACTIVE→PAUSED (either party). PAUSED→ACTIVE (**(A) BD-19**: pausing party only, or either). ACTIVE/PAUSED→CLOSED (either party, reason required). ACTIVE→COMPLETED (**(A) BD-19**: mutual confirmation recommended). CLOSED→ACTIVE only through an accepted `ConnectionReopenRequest` (new model). COMPLETED is terminal. A system close on account deletion preserves history. |
| **Conversation** | Status becomes derived from the connection (section E #11) |
| **Photo access request** (statuses were undefined) | PENDING→APPROVED (creates a 7-day, 30-day or manual permission). PENDING→DECLINED. PENDING→CANCELLED (requester). PENDING→EXPIRED (configurable). |
| **Photo / document permission** | ACTIVE→EXPIRED (time). ACTIVE→REVOKED (owner or authorized manager). **A block is evaluated at access time and doesn't mutate the permission.** That preserves records (FR-PRI-001), and unblocking restores access only if the permission is still valid. |
| **PhoneVerification** (undefined) | PENDING→VERIFIED / EXPIRED / FAILED (attempts exhausted) / SUPERSEDED (resent) |
| **Payment** | Add EXPIRED (abandoned). Allow FAILED/EXPIRED→SUCCEEDED **only through verified reconciliation**, because gateways can confirm late. SUCCEEDED→REFUNDED/PARTIALLY_REFUNDED. |
| **Subscription** | Replace the status "CANCELLED while still active" with a `cancel_at_period_end` flag. Status stays ACTIVE until `ends_at`, then becomes EXPIRED. PENDING→EXPIRED if never paid. The renewal path depends on **(A) BD-20**. |
| **Credit allowance** | EXHAUSTED→ACTIVE only through a compensating refund to the allowance (if BD-16 allows it). Expiry is permitted from both ACTIVE and EXHAUSTED. |
| **Moderation report** (undefined) | SUBMITTED→TRIAGED→CLOSED_ACTIONED / CLOSED_NO_ACTION / DUPLICATE |
| **Appeal** (undefined) | SUBMITTED→UNDER_REVIEW→UPHELD (action reversed via service) / REJECTED. SUBMITTED→WITHDRAWN. |
| **Moderation case** | Add UNDER_REVIEW→OPEN (unassigned) |
| **Export** | PROCESSING→FAILED→PROCESSING (bounded retry). Pre-processing states→CANCELLED. |
| **Account deletion** | REJECTED only for an invalid or failed identity confirmation. **Retention holds don't reject a deletion; they keep only the held records.** PROCESSING never moves backwards; failed steps retry. |

## 4. Detailed Technical Recommendations

**1. Authentication (TR-01).**
- **Web:** Django session cookie (`HttpOnly`, `Secure`, `SameSite=Lax`), served same-origin (TR-13).
  - CSRF uses Django's double-submit cookie. **Set `CSRF_COOKIE_HTTPONLY=False`** (the CSRF token isn't a secret, and the SPA must be able to read it).
  - Session lifetime: 7-day idle timeout, 30-day absolute.
- **Mobile:** an opaque access token (15 minutes) and an opaque refresh token (30-day rolling, 90-day absolute). Both are stored **only as SHA-256 hashes** in `AuthSession` and kept on the device in Expo SecureStore.
  - The refresh token rotates on every use.
  - Reusing an old refresh token revokes the whole session family.
- **Both clients:**
  - Every login creates an `AuthSession` row (device, user agent, IP, approximate location), which drives `/auth/sessions/` listing and revocation.
  - Each request re-checks that the account is active and unrestricted, so a deactivated account can't continue on an existing session.
  - Password reset or a security event revokes all sessions.
- **Rate limits:** login 5 per 15 minutes per phone+IP. OTP limits as documented. Counters are kept in Redis in production.
- **Why not JWT:** a JWT can't be revoked before it expires and can't be listed per device. JWT checks the database anyway for active status, and opaque tokens need no new dependency.
- **Alternative:** djangorestframework-simplejwt with its blacklist (lacks refresh-token reuse detection).

**2. Interest lifecycle.** Section D, with BD-10 to BD-14.

**3. Visibility and eligibility.** One `eligibility` service returns allow or deny with an *internal* reason code. Externally, it returns a generic `not_found`/`not_permitted`, so hidden and blocked relationships aren't revealed. It takes three inputs:
- **Discoverable(target, viewer):**
  - target `profile_status=ACTIVE`, `visibility=VISIBLE_IN_MATCH_SEARCH`
  - target's account is active, not deactivated, and has no pending deletion
  - identity is approved
  - target has no restriction of type `PROFILE_VISIBILITY`, `SEARCH` or `FULL_ACCOUNT`
  - not blocked in either direction (BD-22)
  - target hasn't hidden the viewer
  - hard preference rules pass
- **CanInitiate(actor, target):** Discoverable, plus the actor's own tier (BD-02), the `REQUESTS` restriction, cooldowns, and no existing connection.
- **CanCommunicate(connection, actor):** connection ACTIVE, no block in either direction, no `MESSAGING` restriction.

Moderation restrictions (the `UserRestriction` model) are pulled forward to Phase 6, so every check enforces them from day one.

**4. Request credit refunds.** BD-16. Mechanically, a refund is a `CREDIT` ledger entry with `source=REFUND` that references the original debit. It is idempotent, keyed on `refund:<request_id>`.

**5. Renewal and allowances.** BD-20 and BD-21.
- Allowances are issued per **monthly allowance period** within the billing term, by an idempotent daily Celery job. Uniqueness on (subscription, period_start, credit_type) prevents double issue.
- At period end, an `EXPIRY` ledger entry zeroes the remainder.
- A plan duration is expressed in **months** (`duration_months`) rather than days, so allowance periods align with the term.

**6. Field locking.** BD-05 decides the list.
- Enforcement lives in the profile service: after approval, those fields are read-only in every serializer, and the service rejects any change.
- Changes go through `ProfileFieldCorrectionRequest` (TR-06), reviewed by verification staff and audited.
- Discovery shows a display name (first name, or first name plus initial), never the full legal name.

**7. Admin (TR-07).**
- Django Admin at a non-default path, available only to `is_staff` accounts with MFA enforced (django-otp TOTP + backup codes). Admin sessions: 30-minute idle, 8-hour absolute. Optional IP allowlist at Nginx.
- RBAC uses Django Groups (Support, Moderator, VerificationReviewer, Finance, SystemAdmin) and custom model permissions such as `verification.view_identity_document`. `AdminRoleAssignment` adds `assigned_by`, `expires_at` and `revoked_at`. **This replaces the custom AdminRole and AdminPermission tables** (doc 03 §16.2–16.4, which were only "recommended").
- Status fields are read-only in admin. Admin actions call domain services, so there's no raw state editing.
- Identity documents are served only through an audited proxy view.
- Superuser is reserved for break-glass access, which is audited.

**8. Acting-profile context (TR-08).**
- Every profile-scoped endpoint reads the `X-Acting-Profile: <uuid>` header. If it's absent, the context defaults to the caller's own personal profile. If there's neither, the request fails with `400 acting_profile_required`.
- A single resolver builds an immutable `ActorContext(account, represented_profile, authorization|None, is_owner, granted_permissions, billing_account)`. It is **resolved fresh on every request and never cached**.
- Views declare `required_manager_permission = "send_requests"`, and a DRF permission class enforces it. An unknown or unauthorized acting profile always returns the same error.
- Audit and history rows take `actor_user` and `represented_profile` from the context. Billing uses `represented_profile.owner`.
- **Why a header rather than a path prefix:** resource URLs stay stable across web and mobile, switching profiles is trivial, and it works uniformly in all 16 modules.

**9. Profile-view billing (TR-09)**, implementing DEC-01/02. Within one transaction:
1. Resolve the context.
2. Run the eligibility check.
3. Apply the BD-17 exemptions.
4. Run `SELECT … FOR UPDATE` on the billing account's `CreditWallet` row, which serialises all view charges for that account.
5. Look for a billable `ProfileView` for (billing_account, target) within the last 24 hours. If one exists, record a non-billable view.
6. Otherwise lock the active allowance rows, consume the subscription allowance first and the purchased credit second, write the ledger entry, then the `ProfileView`, then the visitor-history entry.
7. On zero balance, apply BD-18.

The `Idempotency-Key` header makes client retries harmless. The behaviour is tested with concurrent threads on PostgreSQL.

**10. Constraints and concurrency (TR-10).**

| Invariant | Mechanism |
|---|---|
| One active/pending request per pair | Partial unique index on `(LEAST(s,r), GREATEST(s,r)) WHERE status='PENDING'`, plus `CHECK s<>r` |
| One live interest per pair | Same pattern `WHERE status IN ('PENDING','RECIPROCATED')` |
| One connection per pair | `CHECK profile_one_id < profile_two_id` + unique (p1, p2) + request OneToOne |
| One live authorization | Partial unique (profile, manager) `WHERE status IN ('PENDING','ACTIVE','PAUSED')` |
| Never-negative balances | `CHECK purchased_* >= 0`. Allowance `CHECK 0 <= remaining <= granted`. |
| Idempotent ledger | Unique (account, idempotency_key) on CreditTransaction |
| Payments | Unique `merchant_reference`. Partial unique (gateway, gateway_transaction_id). Webhook dedupe on (gateway, event key or payload hash). |
| One paid active subscription | Partial unique (user) `WHERE status='ACTIVE' AND is_paid` |
| No overlapping billing terms | PostgreSQL exclusion constraint on `tstzrange` (`btree_gist` extension) |
| One live export or deletion request | Partial unique (user) on non-terminal statuses |
| Case-insensitive email | Unique `Lower(email)` |

Cross-table checks such as cooldowns, "connection exists" and eligibility can't be expressed as constraints. They are serialised with `pg_advisory_xact_lock(hash(ordered pair))`.

**Fixed lock order** (to avoid deadlocks): pair lock → wallet → allowances → request or interest row.

An `IntegrityError` caught from a constraint backstop is turned into the domain error. `IdempotencyRecord` (scope, account, key, request hash, response snapshot) covers financial POST endpoints.

**11. Uploads (TR-11).**
1. Nginx and Django enforce size caps.
2. Content type is detected from the file bytes (`filetype`), not trusted from the extension or MIME header. An allowlist applies per storage group.
3. The file is stored under an opaque UUID key in a **quarantine** prefix. Original filenames are never used in keys.
4. A Celery task scans it (EP-06) and then processes it.
5. For images, the task:
   - opens and verifies with Pillow, enforcing `MAX_IMAGE_PIXELS` against decompression bombs
   - applies the EXIF orientation
   - **re-encodes to strip all metadata (EXIF/GPS/XMP)**
   - generates the card, thumbnail and full-size versions
   - **discards the original**

   Photos then enter moderation as PENDING.
6. PDFs (documents and attachments) are scanned but never rendered server-side. Downloads are forced with `Content-Disposition: attachment` and `nosniff`.
7. Each storage group (photos, identity, attachments, documents, evidence, exports) gets its own prefix, IAM policy and, for identity documents, its own KMS key.
8. Delivery uses signed URLs with a 60–300 second TTL for photos, and an authorised proxy (immediately revocable) for identity documents, shared documents and exports.
9. Locally, `MEDIA_ROOT` is never URL-mapped. Files are served only by authorised views.

**12. Audit and outbox (TR-12).**
- **Audit:** `record_audit_event(ctx, action, resource, result, safe_metadata)` writes inside the business transaction, so the audit entry exists if and only if the change committed. Denied or failed security events are written in a fresh transaction after the rollback.
  - The log is append-only through three layers: the model refuses updates, admin is read-only, and **a PostgreSQL trigger rejects UPDATE and DELETE** on the table.
  - Metadata is allowlisted and redacted. Action codes are constants such as `family.authorization.revoked`.
  - Domain histories remain in their own modules.
- **Outbox:** `publish_event(type, aggregate, ids_only_payload, idempotency_key)` writes to `OutboxEvent` in the same transaction.
  - Dispatch has a fast path (`transaction.on_commit` enqueues the dispatcher) and a Celery beat sweeper.
  - Workers claim batches with `FOR UPDATE SKIP LOCKED` and a lease timeout. Handlers come from a registry keyed by event type, are idempotent, and **re-read current state and re-check eligibility** (so a blocked party isn't notified).
  - Retries use bounded exponential backoff, ending in `FAILED` plus an alert.
  - Notification records are unique on (event, recipient, channel).
  - Without Celery locally, a `process_outbox` management command replaces the workers.

## D. Proposed Interest Database Model and State Machine

This is PROPOSED. Items tied to BD-10 to BD-14 aren't final.

**`Interest`** (Module 07)
- `id` UUID · `sender_profile` FK PROTECT · `receiver_profile` FK PROTECT
- `status`: `PENDING | RECIPROCATED | CONVERTED_TO_REQUEST | DECLINED | WITHDRAWN | EXPIRED | CLOSED`
- `formal_request` OneToOne → MatrimonialRequest, nullable
- `sent_at`, `responded_at`, `expires_at` (nullable, BD-11), `closed_at`, `closure_reason` (`BLOCKED | ACCOUNT_DELETED | PROFILE_SUSPENDED | PROFILE_CLOSED | INELIGIBLE`)
- `created_by` and `updated_by` (actual accounts) · `created_at`, `updated_at`
- No free-text message field [TR]. That keeps interests lightweight and avoids an unmoderated messaging channel.

**Constraints:**
- `CHECK sender_profile <> receiver_profile`
- Partial unique on the unordered pair `WHERE status IN ('PENDING','RECIPROCATED')`
- Indexes on (receiver, status, sent_at), (sender, status, sent_at) and (status, expires_at)

**`InterestHistory`** (append-only): `interest`, `action`, `previous_status`, `new_status`, `performed_by`, `performed_for_profile`, `reason`, `metadata`, `created_at`.

**`DirectionalCooldown`** replaces `RequestCooldown`. This is a schema generalisation; the decided rules are unchanged.
- Fields: `sender_profile`, `receiver_profile`, `source_type` (`INTEREST | REQUEST`), `source_id`, `reason` (`DECLINED | EXPIRED`), `starts_at`, `ends_at`, `created_at`
- Unique (source_type, source_id). Index (sender, receiver, ends_at).

**State machine:**
```
PENDING ──receiver: show interest back──────────▶ RECIPROCATED
PENDING ──receiver: send formal request─────────▶ CONVERTED_TO_REQUEST
PENDING ──receiver: decline─────────────────────▶ DECLINED   (+30-day cooldown sender→receiver) [DECIDED]
PENDING ──sender: withdraw──────────────────────▶ WITHDRAWN  (no cooldown)
PENDING ──expiry job (BD-11)────────────────────▶ EXPIRED    (no cooldown)
PENDING/RECIPROCATED ──system event─────────────▶ CLOSED     (block, deletion, suspension)
RECIPROCATED ──either party: send formal request▶ CONVERTED_TO_REQUEST
Terminal: CONVERTED_TO_REQUEST, DECLINED, WITHDRAWN, EXPIRED, CLOSED
```

**Workflow rules:**
1. **Create:** pair advisory lock, then CanInitiate. That includes the interest cooldown, the request cooldown (if BD-12 is approved), any existing live interest, pending request or connection, and the rate limit (BD-10). If the reverse-direction interest is PENDING, the service **reciprocates it instead of creating a duplicate**. Then history and the outbox event `interest.received` (generic content).
2. **Convert:** a single transaction that locks the interest, creates the formal request through the request service (credit deducted from the **converting party's owning account**, consistent with formal-request rules), links `formal_request`, and writes both histories and the outbox event.
3. **Hide:** a pending interest *from* a profile the owner later hides stays pending. Hiding doesn't terminate existing relationships (DEC-07).
4. **Managers:** sending requires `send_interests`; responding requires `respond_to_interests`. `performed_by` and `performed_for_profile` are always recorded.
5. **Tests:** T-INT-001…015 cover duplicates in both directions, auto-reciprocation, directional cooldown (reverse allowed), the conversion credit charged exactly once under concurrency, closure on block, and manager permission denial.
