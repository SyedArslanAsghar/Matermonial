## C17. Account-state locking

### 17.1 The anchor row [TR]

**The `User` row is the account's lock anchor.** It always exists, unlike `AccountDeletionRequest`.

**Every account-state change takes `User FOR UPDATE` before doing anything else.** That covers:
- deactivation and reactivation
- creating a deletion request, cancelling it, and moving it to PROCESSING
- applying or lifting an account-level `UserRestriction`
- an admin changing `is_active`

Creating an `AccountDeletionRequest` happens **while holding the User row lock**.

**Every operation that depends on an account's state takes `User FOR SHARE`** on each relevant account, then reads `is_active`, the restrictions and the deletion request.

**Why this closes the "no deletion request yet" race.** A dependent operation holding `User FOR SHARE` blocks the creation of a deletion request, because creation needs `FOR UPDATE` on the same row. The reverse also holds: a deletion request being created blocks the dependent operation until it commits, and the dependent operation then sees the new request. A partial unique index allowing one non-terminal deletion request per user (`status IN (REQUESTED, IDENTITY_VERIFICATION_REQUIRED, PENDING_RECOVERY, PROCESSING)`) is the backstop (DCR-61).

### 17.2 Which accounts each operation locks

`ACC(...)` means: `SELECT … FROM user WHERE id IN (…) ORDER BY id FOR SHARE`. PostgreSQL locks rows in the order they're returned, so ordering by ID gives a deterministic order. Duplicates are removed first.

| Shorthand | Accounts included |
|---|---|
| **ACC-pair** | The actual account (if it's a manager) + the owner of the represented profile + the owner of the counterparty profile |
| **ACC-self** | The actual account (if it's a manager) + the owner of the represented profile |

### 17.3 Rule for exclusive-lock transactions [TR, new; prevents cycles]

A transaction that takes `FOR UPDATE` on a `User` row or a profile-status row:
- locks **exactly one anchor**
- may afterwards lock only rows belonging to that anchor (its deletion request, restrictions, sessions, tokens, its own profiles)
- **must not take pair locks, wallets, allowances, or any other account's or profile's rows**

Effects on other parties (cancellations, closures, refunds) run as **separate fan-out transactions after commit**. A transaction also never takes `FOR SHARE` and then `FOR UPDATE` on the same row, which avoids lock-upgrade deadlocks.

### 17.4 Implicit foreign-key locks (new contradiction C-26) [TR-23]

**The problem:** inserting a row that has a foreign key quietly takes `FOR KEY SHARE` on the row it points to, and that conflicts with `FOR UPDATE`.

**Example:** a refresh holds `AuthSession` and inserts an `AccountSecurityEvent` pointing at `User`. Meanwhile, a deletion holds `User FOR UPDATE` and waits for `AuthSession`. That's a deadlock.

**Fix:**
- (a) Every authentication flow takes `User FOR SHARE` first (§17.5).
- (b) The append-only logs `AuditLog`, `AccountSecurityEvent` and `OutboxEvent` store actor, subject and profile IDs as **plain UUID columns with no database foreign key**. This also keeps those records intact after deletion pseudonymises the account (FR-DAT-009).
- ProfileView and the ledger keep their foreign keys. The rows they point to are already share-locked in the same transaction (§21).

## C18. Profile-state locking

### 18.1 Two separate lock types [TR]

| Lock | What it is | What it protects | Modes |
|---|---|---|---|
| **Profile lock** | A row lock on `MatrimonialProfile` (level 3) | Profile status, visibility mode, profile-level restrictions and the identity hold. Anything that changes these takes `FOR UPDATE` on that one profile row (§17.3). | `FOR SHARE` for dependent operations, on all relevant profiles, ascending ID, **always before pair locks** |
| **Pair advisory lock** | A transaction-level advisory lock on a synthetic key built from the pair (level 4) | Pair relationship state: blocks, hides, cooldowns, interests, requests, connection, reopen requests | Exclusive for changes. Shared for operations that need that state to stay put but don't change it. |

They don't stand in for each other. A profile lock doesn't stabilise pair state, and a pair lock doesn't stabilise profile status.

Profile-status changes use **`FOR UPDATE`**, as you instructed. These include the owner pausing or resuming the profile, suspension and its lifting, closure, an identity decision that changes `identity_verified_at` or creates the restrictive hold, profile-level restrictions, and visibility-mode changes.

### 18.2 Protective actions [TR]

Some actions must always succeed, whatever state the counterparty is in, because they reduce exposure:
- block, unblock
- add or remove from Hide My Profile From
- close a connection, pause a connection
- revoke a document permission
- authorization pause, revoke, resign

These take **ACC-self only, no profile locks**, plus the exclusive pair lock where pair state changes. Unblocking still doesn't restore eligibility on its own [DECIDED, FR-PRI-002], because eligibility is re-checked by every dependent operation.

### 18.3 Services you named

`PRF(A,B)` means `FOR SHARE` on both profiles, ascending ID.

| Service | Profile locks | Pair lock |
|---|---|---|
| Send message / upload attachment | PRF(both) | Shared |
| Document share | PRF(both) | Exclusive |
| Document access | PRF(both) | Shared |
| Document revoke | None (protective) | Exclusive |
| Profile-view POST | PRF(viewer profile, target) | Shared |
| Connection resume, complete, reopen, progress update | PRF(both) | Exclusive |
| Connection pause, close | None (protective) | Exclusive |
| All interest and request operations | PRF(both) + sender quota advisory lock (express interest only) | Exclusive |

## Revised global lock order (ADR-031; replaces v4.1 §15.2)

Locks are acquired in this order. Levels can be skipped, never revisited.

| Level | Locks |
|---|---|
| 1 | **Authorization row:** `FOR SHARE` (delegated action) or `FOR UPDATE` (pause, revoke, permission change) |
| 2 | **Account:** `User` rows first (`FOR SHARE`, ascending, for dependents; `FOR UPDATE` on a single account for state changes). Then, for one account only: AccountDeletionRequest → account-level UserRestriction → UserSubscription → SubscriptionBillingPeriod → Payment / RefundRequest / AdjustmentRequest → AuthSession → AuthToken. **(v4.1's order AccountDeletionRequest → User is reversed; C-24.)** |
| 3 | **Profile:** `MatrimonialProfile` rows (`FOR SHARE`, ascending, for dependents; `FOR UPDATE` on a single profile for status changes, or on the account's own profiles during deletion). Then profile-level restriction or identity-hold rows. Then profile quota advisory locks. |
| 4 | **Pair advisory locks:** shared or exclusive, ascending key |
| 5 | **Wallet** `FOR UPDATE` (only one per transaction) |
| 6 | **Allowances** `FOR UPDATE`, ordered by `expires_at, id` |
| 7 | **Domain rows**, in type order: ProfileBlock → HiddenProfile → DirectionalCooldown → Interest → MatrimonialRequest → ProfileConnection → ConnectionReopenRequest → RelationshipProgress → Conversation → DocumentPermission |
| 8 | **Inserts only**, in this order: CreditRefundOperation / CreditRefundLine → CreditTransaction → domain records (history, ProfileView, VisitorHistory, Message, access history, ManagerActionLog, ProfileAccessHistory) → AccountSecurityEvent → AuditLog → OutboxEvent |

Unchanged from v4.1: §17.3, one aggregate per transaction, no external calls inside a transaction, retry on 40P01 / 40001 / 55P03 up to 3 attempts, and the `LOCK_PLAN` tracker (TR-22, now also covering levels 2–3).

## C19. Pause constraint (replaces the v4.1 §14.1 constraint)

**The flaw in v4.1:** the constraint `(status='PAUSED') = (by IS NOT NULL AND at IS NOT NULL)` let through partial states such as status ACTIVE with `paused_by_profile` set and `paused_at` NULL, because false = false (C-29).

**Corrected constraint [TR]:**

```sql
CONSTRAINT connection_pause_state_consistent CHECK (
  (status = 'PAUSED'
     AND paused_by_profile_id IS NOT NULL
     AND paused_at IS NOT NULL
     AND paused_by_profile_id IN (profile_one_id, profile_two_id))
  OR
  (status <> 'PAUSED'
     AND paused_by_profile_id IS NULL
     AND paused_at IS NULL
     AND pause_reason IS NULL)
)
```

**Supporting rules:**
- `status`, `profile_one_id` and `profile_two_id` are `NOT NULL`, so the `IN` comparison can never evaluate to NULL.
- `pause_reason` is optional while paused and must be NULL otherwise.
- `paused_by_account` isn't a column on this row. It's recorded only in `ConnectionHistory` (v4.1).
- Every exit from PAUSED (resume, close, complete) clears all three fields in the same UPDATE.

**Tests (T-CON-077…080):** each partial state raises an `IntegrityError` at the database level (pauser set without a time, time without a pauser, pauser not in the pair, pause fields left behind after resume or close).

## C20. Refund idempotency and T7–T10 notifications

### 20.1 Refund model [TR; amends DCR-46]

**`CreditRefundOperation`** (the parent record):
- `id`, `account`, `source_type` (REQUEST_CANCELLATION, …), `source_id`, `original_operation_id`
- `outcome` (REFUNDED | PARTIALLY_LAPSED | LAPSED), `created_at`
- **`UNIQUE (source_type, source_id)`**: at most one refund operation per cancelled request

**`CreditRefundLine`** (one per original debit row):
- `refund_operation`, `original_transaction` (the debit row), `bucket`, `amount`
- `disposition` (REFUNDED | LAPSED)
- `refund_transaction` (nullable)
- **`UNIQUE (original_transaction)`**: a debit row can only ever be refunded or lapsed once
- `CHECK ((disposition='REFUNDED') = (refund_transaction_id IS NOT NULL))`

**Ledger rows:** each REFUNDED line has one `CREDIT/REFUND` row with idempotency key **`refund:<refund_operation_id>:<original_transaction_id>`**, covered by the existing `UNIQUE (account, idempotency_key)`.

**Flow** (inside the cancelling transaction, after the wallet and allowance locks):
1. The conditional status update `PENDING → CANCELLED` must affect exactly 1 row. If it affects 0, the request was already handled and nothing else happens.
2. `INSERT CreditRefundOperation … ON CONFLICT (source_type, source_id) DO NOTHING`. If nothing was inserted, the refund has already been done and nothing else happens.
3. For each debit row of `original_operation_id`, insert a line: REFUNDED to the same bucket, or LAPSED if that allowance has expired (OD-07d). Write the ledger row and update the projection for REFUNDED lines.
4. Set the parent's outcome.

**Three independent guards** (the status transition, parent uniqueness, line uniqueness) plus ledger key uniqueness give exactly-once behaviour under retries, concurrent fan-out and reruns.

**Source of truth:** v4.1's `MatrimonialRequest.refund_outcome` is **removed** because it duplicated the refund record (C-27). The refund outcome comes from the `CreditRefundOperation` for that request.

**Tests:**
- T-REQ-035: a mixed-bucket debit gives one parent and N lines.
- T-REQ-036: concurrent fan-out with a retry still gives one parent.
- T-REQ-037: a manual duplicate line insert is rejected.
- T-REQ-038: projection = Σ ledger after a partial lapse.

### 20.2 Notifications for sender-side cancellations T7–T10 [REC-BIZ, OD-07f]

| Trigger | Sender | Recipient |
|---|---|---|
| T7 Sender deletion PROCESSING | No notification (already told about deletion; account being removed) | **No notification.** The item shows "No longer pending" in their list. |
| T8 Sender suspended | No per-request notice. The moderation notice (owned by D20) says pending requests were cancelled without a refund. The in-app list shows "Cancelled". | Same as T7 |
| T9 Sender closes profile | **The closure confirmation warns** beforehand that pending requests will be cancelled without a refund. No notice afterwards. | Same as T7 |
| T10 Sender blocks recipient | None (the sender did it) | Same as T7. **Must not reveal the block** [DECIDED]. |

**Consistency rule:** for every sender-side cancellation (T7–T10), the recipient sees the **same** neutral item status and receives no push, SMS or email. For recipient-side cancellations (T3–T6), the uniform "No longer pending, credit returned" message to the sender from v4.1 still applies.

## C21. Where ProfileView and VisitorHistory sit in the lock order

**Classification [TR]:**
- **ProfileView** and **VisitorHistory** are **level 8, insert only**.
- They're never locked with `FOR UPDATE` and never updated.
- VisitorHistory removal is a separate insert (`VisitorHistoryRemoval`).
- Retention purges run as batch deletes outside business transactions, under the retention policy, and never touch ProfileView before its financial retention period ends.

**Profile-view POST, in order:**

| Step | Action | Lock |
|---|---|---|
| 1 | Authorization | S* |
| 2 | ACC-pair | User `FOR SHARE` |
| 3 | PRF(viewer profile, target) | Profile `FOR SHARE` |
| 4 | Pair advisory lock | **Shared**. Serialises with block and hide; doesn't serialise with other views. |
| 5 | Billing wallet `FOR UPDATE` | This serialises the 24-hour window check per billing account. The check is a plain SELECT on ProfileView, using index `(billing_account, target_profile, viewed_at)`, done after this lock. |
| 6 | Allowances `FOR UPDATE` | Only if a billable debit is needed |
| 7 | **CreditTransaction** insert (debit), plus the projection update on rows already locked in steps 5–6 | — |
| 8 | **ProfileView** insert (its FK to the CreditTransaction is the row just inserted) | — |
| 9 | **VisitorHistory** insert, if the visitor-history feature applies (private visits: identity NULL) | — |
| 10 | **AuditLog** insert (soft references, TR-23) | — |
| 11 | **OutboxEvent** insert, if any notification applies | — |

**No new locking added:**
- ProfileView's foreign keys point to the viewer user, the viewer profile, the target profile and the credit transaction. All are already share-locked or inserted in this transaction, so the implicit `FOR KEY SHARE` locks are compatible.
- A non-billable view inside the 24-hour window skips steps 6–7.
- The GET endpoint takes no locks.

## C22. Effects of COMPLETED → CLOSED

This applies the same way to any transition into CLOSED. COMPLETED-origin closures additionally can't be reopened (v4.1 C12).

| Area | Effect | Basis |
|---|---|---|
| Profile-detail access | The connection-derived access (L3, connection-based L2, connection billing exemption) **ends**. The pair falls back to the v4 §9 "Connection CLOSED" row: VIS → unrelated-viewer rules; VAA → L1 history card; HID → L1 history card. | REC-BIZ, OD-03j (unchanged) |
| New communication | **Ends.** No new messages, attachments or document shares. Messaging needs an active connection [DECIDED]. | DECIDED |
| Conversation history | **Kept.** Both participants keep **read-only** access to the existing conversation, subject to the existing access rules (block in either direction → no access, v4 §9). **No message is deleted or hidden because of the closure.** Messages remain subject only to the existing retention rules (doc 15 §8: "Existing messages remain subject to retention and access rules"; doc 03 §19; DataRetentionPolicy). Retention periods not yet defined stay open under doc 13 OD-005. | DECIDED (retention unchanged) |
| Shared documents | Permission rows aren't deleted. They keep expiring or being revoked under their own lifecycle, and access history is kept. **New access attempts are denied while the connection is CLOSED**, because document access is defined for connected profiles (glossary: "Shared Document"). | REC-BIZ, OD-06l (extended) |
| Photo permissions | Unaffected. Separate control [DECIDED, FR-PRO-006 / doc 05 rule 11]. | DECIDED |
| Relationship progress and shared notes | Stage frozen, "Closed" label derived. Notes stay readable to both parties as history, but can't be edited. | REC-BIZ, OD-06l |
| Moderation-driven closure | Read access to history can be further restricted only by an explicit moderation action, using the existing D20 tools. The closure itself doesn't restrict it. | DECIDED (moderation rules) |
| Account deletion of a party | Handled by the existing deletion rules for messages. Unchanged. | DECIDED |
| Reopening | Not allowed when `closed_from_status = COMPLETED` | REC-BIZ, OD-06l |

**Tests (T-CON-090…095):**
- After closure: sending is denied; history is readable; the message count is unchanged.
- Document access is denied, but the permission row still exists.
- Photo permissions are unchanged.
- A block makes history unreadable.
