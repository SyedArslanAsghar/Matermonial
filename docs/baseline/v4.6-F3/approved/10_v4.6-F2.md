## 1. SHRED_INTENT: linking each key to its KEK version, and CACHE_INSERT (amends DCR-97)

**Affected sections:**
- v4.6-F1 Correction 3: the SHRED_INTENT and SHRED_COMPLETED params, and recovery rule 4
- v4.5 §2.1: the `ShreddedPseudonym` cache
- v4.6-F §A.2: the data classes allowed in Stream R (unchanged)

### Revised specification text (replaces the SHRED_INTENT / SHRED_COMPLETED params in v4.6-F1 Correction 3)

> **`SHRED_INTENT` params (Stream R):**
> ```json
> {
>   "pseudonym": "<subject pseudonym>",
>   "subject_type": "ACCOUNT | PROFILE",
>   "keys": [
>     { "key_id": "<opaque key id>", "kek_version": "<kek version at intent>" }
>   ],
>   "actions": ["DESTROY_KEYS", "UNLINK_PSEUDONYM", "CACHE_INSERT"],
>   "cache_insert": {
>     "table": "shredded_pseudonym",
>     "key": "<same pseudonym>",
>     "row": { "subject_type": "ACCOUNT | PROFILE", "keys_digest": "<sha256 of JCS(keys)>" },
>     "expiry": "NONE"
>   },
>   "holds_active_at_intent": 0
> }
> ```
>
> **Rules for `keys`:**
> - At least one entry.
> - Sorted by `key_id`, with `key_id` unique within the array.
> - Each entry pairs one data key with the KEK version that wrapped it **when the INTENT was written**.
> - The separate `key_ids` and `kek_versions` arrays from v4.6-F1 are **removed**.
>
> **Privacy:** only a pseudonym, opaque key IDs, KEK version labels and operational values appear. No direct identifiers (v4.6-F §A.2).
>
> **`CACHE_INSERT` is fully specified. Recovery derives nothing by guesswork.**
> - **Target:** table `shredded_pseudonym`, primary key `pseudonym`.
> - **Row values:**
>   - `subject_type` and `keys_digest`, taken from `params.cache_insert.row`
>   - `op_id`, `intent_seq` and `intent_entry_hash`, taken from the **verified header** of the SHRED_INTENT entry. They're not in `params`, so there's no circular dependency (v4.6-F1 Correction 1).
>   - `shredded_at`, set to the apply time
> - **Expiry: `NONE`.** The row is never removed automatically. It holds only an unlinked random pseudonym and opaque digests. It keeps shredding idempotent and stops re-linking if a restored backup still contains the pseudonym. Any shorter retention can only come from the legal-review retention decision (doc 13 OD-005), applied as a Stream M maintenance operation.
> - **Re-apply:** `INSERT … ON CONFLICT (pseudonym) DO NOTHING`. If a row exists, its `op_id` and `keys_digest` must match. A different `op_id` or digest → integrity alarm, and the operation goes to `BLOCKED_OPERATOR`.
>
> **Key destruction, including after a restore.** For each entry in `keys`:
> 1. Look up the `SubjectDataKey` row by `key_id`.
> 2. **Absent:** record it in `not_present_keys`. That's not a failure (v4.6-F1 rule 4).
> 3. **Present with `kek_version` = the recorded version:** destroy it (tombstone, v4.5 §2.2).
> 4. **Present with a different `kek_version`:** that's allowed **only if** Stream M has a COMPLETED `KEK_ROTATE` chain connecting the observed version to the recorded version, in either direction. That chain is how re-wrapping legitimately changes a key's version, for example a rotation after the INTENT, or a backup taken before an earlier rotation. If such a chain exists, destroy the key and record `observed_kek_version`. If not → integrity alarm and `BLOCKED_OPERATOR`. **The association is never guessed.**
>
> **`SHRED_COMPLETED` params:**
> ```json
> {
>   "destroyed_keys": [
>     { "key_id": "…", "recorded_kek_version": "…", "observed_kek_version": "…" }
>   ],
>   "not_present_keys": [ { "key_id": "…", "recorded_kek_version": "…" } ],
>   "cache_row": { "pseudonym": "…", "op_id": "…", "keys_digest": "…" }
> }
> ```
>
> **Verification (step 8 in v4.6-F B.2):**
> - Every recorded key is either tombstoned or listed as not present.
> - The pseudonym is unlinked.
> - The cache row exists with matching `op_id` and `keys_digest`.
> - No live wrapped key remains for the pseudonym.

## 2. Retention of DEAD_UNDECRYPTABLE financial events (amends DCR-98)

**Affected sections:**
- v4.6-F1 Correction 4: the restore step, the terminal-status list, and "`dedupe_key` redacted"
- v4.6 §1.3: the redaction trigger and redaction schedule
- v4.4 §3.4: reconciliation

### Revised specification text (replaces the DEAD_UNDECRYPTABLE parts of v4.6-F1 Correction 4)

> **New columns on financial events.** OutboxEvent rows with `event_class = FINANCIAL_OBLIGATION` carry:
> - `obligation_resolution`: `PENDING` | `REPLACED_VERIFIED` | `OBLIGATION_SATISFIED_VERIFIED`, default `PENDING`
> - `replaced_by_event_id` (nullable)
> - `resolved_at` (nullable)
>
> **Detection.** When an event can't be decrypted because its queue-key version is destroyed (normally after a restore), the same transaction:
> - sets the event to `DEAD_UNDECRYPTABLE`, with `obligation_resolution = PENDING`
> - inserts `ReconciliationDiscrepancy(type = FINANCIAL_EVENT_UNDECRYPTABLE, outbox_event_id)`
>
> **The `dedupe_key` is not redacted at this point.** That replaces the v4.6-F1 wording (C-74).
>
> **Dedupe uniqueness** becomes a partial unique index:
> ```sql
> UNIQUE (dedupe_key) WHERE status NOT IN ('DEAD_UNDECRYPTABLE','CANCELLED')
> ```
> So a replacement event can be inserted while the original stays intact.
>
> **The obligation comes from domain records, never from the event.** For refunds, the obligation is: `MatrimonialRequest` is CANCELLED with a refundable reason (OD-07) **and** there's no verified `CreditRefundOperation` for it. It's re-derived from domain records every time. An unavailable event or key never removes it.
>
> **Resolution**, done by the reconciliation job in a transaction that locks only the original outbox row:
> - **(a) Obligation still outstanding:** create a replacement event (same business identity, current queue key) and record `replaced_by_event_id`. **The original stays `PENDING`** until the replacement reaches `DONE`, meaning the refund passed verification V1–V5 (v4.5 §3). Only then: `obligation_resolution = REPLACED_VERIFIED` and `resolved_at = now`.
> - **(b) Obligation already satisfied** (a verified `CreditRefundOperation` exists, for example the refund completed in the restored data): `obligation_resolution = OBLIGATION_SATISFIED_VERIFIED`, `resolved_at = now`, and no replacement is created.
>
> In both cases, the same transaction marks the discrepancy resolved and writes an AuditLog event `FINANCIAL_EVENT_UNDECRYPTABLE_RESOLVED`:
> - plaintext: `original_outbox_event_id`, `replacement_outbox_event_id`, resolution type
> - inside the debit account subject's envelope (v4.5 §2.4): the request and refund-operation IDs
>
> **When redaction becomes possible.** The redaction and purge rules (v4.6 §1.3) apply to a FINANCIAL_OBLIGATION event **only when all of these hold**:
> - status is `DONE`, `DEAD_UNDECRYPTABLE` or `DEAD`, and
> - for `DEAD_UNDECRYPTABLE`: `obligation_resolution ∈ {REPLACED_VERIFIED, OBLIGATION_SATISFIED_VERIFIED}` **and** `resolved_at + 7 days ≤ now`
> - for `DEAD`: resolved by an operator intervention
> - for `DONE`: refund verified, and 7 days have passed since `DONE`
>
> Purging follows at 30 days from the same anchor. **An unresolved `DEAD_UNDECRYPTABLE` event is never redacted or purged.** The redaction trigger enforces these conditions on top of the v4.6 terminal-status check.
>
> **Audit evidence is kept separately.** The AuditLog event and the `ReconciliationDiscrepancy` record keep their own retention (the financial and reconciliation categories, subject to legal review, doc 13 OD-005). They don't depend on the outbox row's 7-day redaction or 30-day purge.
>
> **Safeguards:**
> - An unresolved `DEAD_UNDECRYPTABLE` event older than 24 hours raises an alert.
> - **Restore startup gate:** every `DEAD_UNDECRYPTABLE` financial event must either have a live replacement event or be `OBLIGATION_SATISFIED_VERIFIED`, and there must be zero outstanding obligations without a live event.
> - The `QUEUE_KEY_DESTROY` precondition (v4.6-F1) also needs zero unresolved `DEAD_UNDECRYPTABLE` events.

### New and amended tests

| ID | Scenario | Pass condition |
|---|---|---|
| **T-OUT-013** | An unresolved `DEAD_UNDECRYPTABLE` event at 8 and 31 days | Not redacted, not purged. The trigger rejects any manual redaction. |
| **T-OUT-014** | Replacement created but not yet `DONE` | Original stays `PENDING` and not redactable. After the replacement is `DONE` and verified → `REPLACED_VERIFIED`. Redactable only after 7 more days. |
