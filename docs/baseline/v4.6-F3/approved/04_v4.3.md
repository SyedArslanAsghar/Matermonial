## 1. C17.4 in full: implicit foreign-key locks (replaces v4.2 C17.4)

### 1.1 How PostgreSQL behaves

**When a row with a foreign key is inserted** (or its FK column is updated), PostgreSQL checks the referenced row with `SELECT 1 … FOR KEY SHARE`. That implicit lock:
- conflicts with **`FOR UPDATE`** on the referenced row, and with `DELETE` or an update of a key column
- does **not** conflict with `FOR SHARE`, `FOR KEY SHARE` or `FOR NO KEY UPDATE`

A plain UPDATE of non-key columns takes `FOR NO KEY UPDATE`, so it doesn't conflict with that check.

**v4.2 uses explicit `FOR UPDATE`** on `User` (account-state changes) and `MatrimonialProfile` (status changes), as you required. So **any insert anywhere that references a User or profile row being changed will wait** for that state change to finish.

**On delete actions:** `ON DELETE CASCADE` or `SET NULL` on a referenced row locks and changes the rows that point to it.

### 1.2 The hazard

An implicit FK lock is taken at **level 8** (the insert), but it lands on a **level 2 or level 3 row**. In effect, a lock is acquired late and out of order. This is how a deadlock forms:
- Transaction T1 holds some lock L and then inserts a row pointing to User U, so it waits for `KEY SHARE` on U.
- Transaction T2 holds U `FOR UPDATE` and then asks for L.

Each is waiting for the other. The confirmed case from v4.2 is **refresh vs. deletion**: refresh held `AuthSession` and inserted an `AccountSecurityEvent` pointing at User, while deletion held User and waited for `AuthSession`.

### 1.3 Where implicit FK locks occur

| Inserted row | Points to | Already safe? |
|---|---|---|
| Domain history `performed_by` (all history tables) | Actor's User | Yes. The actor is always in the ACC set, so the transaction already holds `FOR SHARE`. |
| History `performed_for_profile`, Interest, Request, Connection, Message rows | Represented and counterparty profiles | Yes for dependent operations (PRF set). For protective actions, see F3. |
| `ProfileBlock.blocked_profile`, `HiddenProfile.hidden_profile` | Counterparty profile | F3 (bounded wait) |
| `ProfileView` (viewer user, viewer profile, target profile, credit transaction) | All share-locked or inserted in the same transaction | Yes (v4.2 C21) |
| `AuthSession.user`, `AuthToken.session` | User, AuthSession | F5 |
| `ManagerActionLog`, `ProfileAccessHistory` (manager, profile, authorization) | Locked at levels 1–3 in the same transaction | Yes |
| `AuditLog` actor and subject, `AccountSecurityEvent.user`, `OutboxEvent` recipients | Any account or profile, including counterparties and accounts not otherwise locked | **No.** Fixed by F2. |

### 1.4 Fixes [TR]

| # | Fix | TR / DCR |
|---|---|---|
| **F1** | **"Reference means prior lock" rule:** every User or profile row that a transaction's inserts will point to (through a database FK) must already be locked by that transaction at its proper level (`FOR SHARE` or stronger) before any later-level lock is taken. A transaction never waits against its own lock, and a competing `FOR UPDATE` holder would have blocked the earlier, correctly ordered share lock instead. | TR-09 / DCR-53 |
| **F2** | **Soft references for append-only logs:** `AuditLog`, `AccountSecurityEvent` and `OutboxEvent` store `actor_user_id`, `user_id`, `subject_*_id`, `represented_profile_id`, `session_id`, `authorization_id` and recipient IDs as **plain UUID columns with no database FK**. That removes implicit locks from the tables written in almost every flow, including flows that mention accounts which aren't locked. It also keeps these records valid after deletion anonymises identifiers (doc 03 §19, FR-DAT-009). Integrity comes from: the service writes only IDs from its own ActorContext or locked rows; a nightly check reports dangling IDs; and the logs are append-only by trigger. | **TR-23 / DCR-60** |
| **F3** | **Allowed bounded waits:** protective actions (block, hide) insert rows pointing to the **counterparty profile** without share-locking it, so the block never depends on the counterparty's state. Their FK check can **wait** while a counterparty profile-anchor transaction finishes. **That can't become a deadlock**, because a profile-anchor transaction takes no further locks after its anchor (§3). The wait is bounded by the anchor transaction's length and `lock_timeout`. | TR-09 / DCR-63 |
| **F4** | **No cascading deletes on hot referenced rows.** FKs to `User` and `MatrimonialProfile` use `PROTECT` (or `SET NULL` only on log-like tables, which use soft references anyway). Accounts are anonymised, not hard-deleted, during business transactions [doc 03 §19]. | TR-09 / DCR-53 |
| **F5** | **Authentication flows take User `FOR SHARE` first** (login, refresh, logout, session revocation), before AuthSession or AuthToken | TR-01 / DCR-54 |
| **F6** | **Detection:** the LOCK_PLAN tracker only sees explicit locks (§6), so implicit locks are covered by F1–F5 by design and checked by the PostgreSQL concurrency tests in §6 | TR-22 / DCR-66 |

## 2. T6 block refund: account-locking gap

### 2.1 Resolution [TR]

**All request refunds move into a separate refund transaction that runs after the cancellation commits**, triggered through the outbox. This applies to T6 and, for consistency, to T2–T5 as well (T1 and T7–T10 have no refund).

**Why this approach:**
- The block transaction no longer touches the sender's financial rows at all, so the protective action never waits on the sender's account state.
- One refund path for every trigger.
- Exactly-once behaviour is already guaranteed by the refund unique keys (§5).

v4.1's "refund inside the cancelling transaction" is replaced by "**refund obligation recorded in the cancelling transaction; refund executed by a dedicated transaction**". The obligation is an `OutboxEvent(REQUEST_REFUND_DUE, request_id)` written atomically with the cancellation, so it can't be lost.

### 2.2 Block transaction: protective, no counterparty locks

1. A `FOR SHARE` (manager path only)
2. ACC-self: User rows `FOR SHARE`, ascending (actor, blocker owner)
3. Exclusive pair lock
4. Domain rows, `FOR UPDATE` in type order: Interest → MatrimonialRequest. Connection is read only.
5. Interests → CLOSED (BLOCKED). Requests → CANCELLED (reason `RECIPIENT_UNAVAILABLE` for T6, `SENDER_UNAVAILABLE` for T10).
6. Inserts: ProfileBlock (implicit `KEY SHARE` on the counterparty profile, F3) → history → AuditLog → OutboxEvent (`REQUEST_REFUND_DUE` for T6; notifications per v4.2 §20.2)
7. Commit

**Counterparty eligibility is never checked or locked.** The block succeeds even if the sender is suspended, deactivated, restricted or being deleted.

### 2.3 Refund transaction (outbox handler, at least once, idempotent)

1. **Sender's billing account User `FOR SHARE`.** This is the debit account recorded on the original ledger rows, not something recomputed from the profile.
2. Level 2 rows: none
3. Profile locks: none (a refund doesn't depend on profile state)
4. Pair lock: none. The request is already CANCELLED, which is terminal, and no pair state is read or changed.
5. Sender wallet `FOR UPDATE`
6. That account's allowances named in the original debit rows, `FOR UPDATE ORDER BY expires_at, id`
7. Domain rows: the request is read only, to confirm `status = CANCELLED` and that its reason qualifies for a refund (OD-07)
8. Inserts per §5: CreditOperation (REFUND) → CreditRefundOperation → refund ledger rows (CreditTransaction) → CreditRefundLine → AuditLog → OutboxEvent (the uniform "No longer pending, credit returned" notice)
9. Commit. A duplicate run finds the existing CreditRefundOperation (`ON CONFLICT DO NOTHING`) and does nothing.

**Account states:**
- If the sender's account is deactivated or in deletion recovery, the refund still lands (financial records are kept).
- If it's in deletion PROCESSING, the refund is still recorded on the ledger. What then happens to the balance follows the existing deletion and financial-retention policy (doc 05 rule 13), unchanged.
- The User `FOR SHARE` lock means the refund serialises cleanly with any account-state change on the sender.

**Latency:** the refund normally lands within seconds. The sender's notification is sent only after the refund commits, so "credit returned" is always true when they see it.

## 3. Exclusive-lock anchors (replaces v4.2 C17.3)

There are two kinds of anchor. **A transaction holds at most one anchor.**

| | **Account-state anchor** | **Profile-state anchor** |
|---|---|---|
| Anchor row | One `User` row, `FOR UPDATE` | One `MatrimonialProfile` row, `FOR UPDATE` |
| Used by | Deactivation and reactivation; deletion request create, cancel and move to PROCESSING; account-level restriction apply or lift; admin `is_active` change | Profile pause and resume by the owner; suspension and its lifting; closure; visibility-mode change; identity decision (`identity_verified_at`, restrictive hold); profile-level restriction |
| **Allowed before the anchor** | **None.** The User row is the first lock. Admin actors aren't locked. | Level 1: the authorization row `FOR SHARE` (manager path, if the action can be delegated). Level 2: ACC-self User rows `FOR SHARE` (owner or manager actor), **not** for staff actions. **Nothing else.** |
| **Allowed after the anchor** | Only that account's own level 2 rows, in order: AccountDeletionRequest → account-level UserRestriction → AuthSession → AuthToken. Then level 8 inserts. | Only that profile's own level 3 rows: profile-level UserRestriction, the identity-verification cycle row, the identity-hold row. Then level 8 inserts. |
| **Prohibited after the anchor** | Any other User row. Any profile row. Pair locks. Wallet. Allowances. Level 7 domain rows. Account-scoped financial rows. | **Pair advisory locks (shared or exclusive), wallets, allowances, any other profile row, any account row, and any level 7 domain row.** |
| Effects on other parties | Separate fan-out transactions after commit, through the outbox | Same |

**Deletion → PROCESSING is now split into two transactions**, so no transaction holds two anchors (replaces the v4.2 matrix row):
- **Tx 1, account anchor:** User U → AccountDeletionRequest (→ PROCESSING) → AuthSession → AuthToken.
- **Tx 2, profile anchor:** ACC-self `FOR SHARE` → own profile U → CLOSED.

Between the two, dependent operations already refuse, because they read the PROCESSING state under User `FOR SHARE`. Then come the fan-out transactions: one per pair, one per authorization, one per refund.

**Consistency with the matrix:** every row taking `Ac U` or `Pr U` has been rechecked. Each shows no Pair, W, Al or D column, and each fans out effects afterwards. The protective action "Profile status change (owner)" already matches: A S*, Ac sh ACC-self, then Pr U self.

## 4. Profile-detail GET consistency [TR; refines TR-19]

**How the GET runs:**
- It executes in **one `READ ONLY` transaction at `REPEATABLE READ`**: a single snapshot, taking no row locks and making no writes.
- Inside that snapshot, the view re-checks the session and account gate, then runs v4 C5 steps 1–9 and reads the profile data. **Every authorization input and the data returned come from the same snapshot.**
- Under READ COMMITTED, an eligibility check could pass on old state and the data read could then see new state. That mixing is ruled out.

**Guarantee (snapshot consistency):**
- Each response is exactly what an authorization decision over **one committed database state** allows.
- A block, hide, profile-status change, account restriction, visibility change or connection change that **commits before the GET's snapshot is taken** is always honoured.
- A GET whose snapshot was taken **just before** that commit may return a response authorised under the earlier state. That window is limited to one in-flight request, bounded by `statement_timeout` (5 s, configurable).
- **No response ever mixes the two states.**
- Nothing caches the result: `Cache-Control: private, no-store`, and no server-side cache of authorization decisions.

**Billing:** the GET writes nothing, so it can't charge. A grant committed concurrently by a POST may not be visible yet, giving a 402 the client resolves by retrying.

**Protected media and documents are enforced on their own:**
- **Document content** is never in the GET response. Each download goes through the document-access service, with its own ACC/PRF share locks, a shared pair lock and a permission check (v4.2 matrix), at request time.
- **Photos:** each signed-URL issuance re-checks photo permission and eligibility. URLs live ≤ 300 s, which is the documented residual window R-8. The URL is never reused across viewers.
- A response's L1/L2/L3 level never grants media or document access by itself.

**Tests:**
- T-CONC-060: a GET racing a block returns either the full pre-block response or a denial, never mixed data.
- T-CONC-061: the same for a profile suspension and for a connection closing.
- T-MAT-022 (no caching) stays.

## 5. Refund integrity [TR; extends TR-15, amends DCR-56]

### 5.1 Supporting structure (minimal)

- **`CreditOperation` header:** `id`, `account_id`, `kind` (DEBIT, GRANT, EXPIRY, REFUND, ADJUSTMENT), `idempotency_key`, `UNIQUE(account_id, idempotency_key)`. This formalises the existing shared `operation_id`. Every `CreditTransaction` has a composite FK `(operation_id, account_id)` → `CreditOperation(id, account_id)`, so all rows of one operation belong to one account.
- **`CreditTransaction`** gains `UNIQUE (id, account_id, operation_id, bucket, amount, direction)` so composite FKs can point at it. `amount > 0`. `direction` is DEBIT or CREDIT. `allowance_id` is NOT NULL for allowance buckets and NULL for purchased buckets (CHECK).
- **`MatrimonialRequest.debit_operation_id`**: FK to CreditOperation, plus `UNIQUE (id, debit_operation_id)`.

**`CreditRefundOperation`** (append-only):
- `id`, `account_id`, `original_operation_id`, `refund_operation_id` (FK to the CreditOperation of kind REFUND, UNIQUE)
- `source_type`, `request_id` (nullable, typed FK)
- `UNIQUE (source_type, request_id)`
- `CHECK (source_type <> 'REQUEST_CANCELLATION' OR request_id IS NOT NULL)`

**v4.2's stored `outcome` is removed.** It's derived from the lines (REFUNDED if every line is refunded, LAPSED if none are, PARTIALLY_LAPSED otherwise), following the source-of-truth rule.

**`CreditRefundLine`** (append-only):
- `id`, `refund_operation_id`, `account_id`, `original_operation_id`
- `original_transaction_id`, `original_bucket`, `original_amount`, `original_direction`
- `disposition` (REFUNDED | LAPSED)
- `refund_transaction_id` (nullable), `refund_amount` (nullable)

### 5.2 Rules: where each is enforced

| Rule | Database enforcement | Service validation (in the refund transaction) |
|---|---|---|
| **Refund account = original debit account** | Composite FK line `(original_transaction_id, account_id, original_operation_id, original_bucket, original_amount, original_direction)` → CreditTransaction unique key. Composite FK line `(refund_operation_id, account_id, original_operation_id)` → `CreditRefundOperation(id, account_id, original_operation_id)` (unique key added). Composite FK parent `(original_operation_id, account_id)` → `CreditOperation(id, account_id)`. Composite FK parent `(refund_operation_id, account_id)` → CreditOperation, with kind REFUND checked by trigger. | Locks exactly that account (§2.3) |
| **Original operation = the debit's operation** | Same first composite FK (`original_operation_id` is part of it). Composite FK parent `(request_id, original_operation_id)` → `MatrimonialRequest(id, debit_operation_id)`. | Loads debit rows by `request.debit_operation_id` |
| `original_direction = DEBIT` | `CHECK (original_direction = 'DEBIT')` | — |
| **Refund bucket = original bucket** | Composite FK line `(refund_transaction_id, account_id, original_bucket, refund_amount)` → `CreditTransaction(id, account_id, bucket, amount)` with direction CREDIT and type REFUND (MATCH SIMPLE, so it's skipped when `refund_transaction_id` is NULL). **Allowance identity:** a `BEFORE INSERT` trigger on the line checks that the original and refund rows have the same `allowance_id` (`IS NOT DISTINCT FROM`). | Picks the bucket from the debit row, never from input |
| **Refund amount ≤ original amount** | `CHECK (disposition='LAPSED' OR refund_amount = original_amount)`. Request refunds are full refunds of each debit row, so equality is stricter than "≤". `CHECK (refund_amount IS NULL OR refund_amount > 0)`. | — |
| Disposition consistency | `CHECK ((disposition='REFUNDED') = (refund_transaction_id IS NOT NULL AND refund_amount IS NOT NULL))` | The decision to lapse (allowance EXPIRED at refund time, read under the allowance lock) is a service rule (OD-07d) |
| **Each debit row refunded at most once** | `UNIQUE (original_transaction_id)` on lines | — |
| **Each refund ledger row used once** | `UNIQUE (refund_transaction_id)` on lines. CreditTransaction rows of type REFUND need `refund_operation_id` NOT NULL (CHECK) | — |
| **One refund per request** | `UNIQUE (source_type, request_id)` | `ON CONFLICT DO NOTHING` means a duplicate run does nothing |
| **Completeness** (every debit row of the operation has a line) | A `DEFERRABLE INITIALLY DEFERRED` constraint trigger at commit: the number of lines for the parent equals the number of DEBIT rows in `original_operation_id` | Builds the lines from the full debit set |
| Only qualifying cancellations refunded | — | The service checks request status CANCELLED and that the reason qualifies under OD-07. Nightly reconciliation cross-checks. |
| **Finalised lines can't be changed silently** | `BEFORE UPDATE OR DELETE` triggers on CreditRefundOperation, CreditRefundLine, CreditOperation and CreditTransaction reject every change. All are final when inserted. | Corrections only through a new compensating ADJUSTMENT operation under dual approval (v3 ledger rule) |
| Projection = Σ ledger | `CHECK ≥ 0` and `remaining ≤ granted` on projections | Projection updated in the same transaction. Nightly reconciliation (v3). |

**Insert order** (level 8): CreditOperation (REFUND) → CreditRefundOperation → CreditTransaction refund rows → CreditRefundLine → AuditLog → OutboxEvent.

**Tests:**
- T-REQ-039…046: one test per database rule, using direct SQL inserts or updates that must be rejected.
- T-REQ-047: an incomplete line set fails at commit.
- T-REQ-048: a lapsed allowance portion.
- T-REQ-049: the derived outcome values.

## 6. LOCK_PLAN tracker scope and PostgreSQL concurrency tests

### 6.1 What the tracker can and can't do [TR-22, clarified]

- **Detects:** explicit locks taken through the project's lock helpers (`select_for_update` / `FOR SHARE` wrappers, advisory-lock helpers), checked against each service's declared LOCK_PLAN and the global order.
- **Can't detect on its own:**
  - implicit FK `KEY SHARE` checks
  - row locks taken by plain UPDATE or DELETE outside the helpers
  - unique-index insertion waits
  - locks from database triggers
  - locks taken by raw SQL that bypasses the helpers
- **How those are covered instead:**
  - by design: F1–F5 and the anchor rules in §3
  - by convention and review: business locks must go through the helpers, and a lint rule flags `raw()`, `extra()` and `cursor.execute` in service modules
  - by the PostgreSQL integration tests below
  - in production: `log_lock_waits=on`, a deadlock-count alert, and a metric on retry rate
- Selected tests also take `pg_locks` snapshots, as a diagnostic aid. **That isn't a completeness guarantee.**

### 6.2 PostgreSQL integration tests (required; TR-13)

**Test method:**
- Run against real PostgreSQL 16, not SQLite.
- Use multiple database connections in threads.
- Force exact interleavings with test-only barriers (advisory locks or hooks injected between steps).
- Set `lock_timeout` so a hang surfaces as a failure instead of blocking the run.
- Mark these tests transactional.
