## 1. Refund worker lock ordering (replaces v4.4 §2.2 steps 1 and 7) [TR-11 revised]

### 1.1 Two-phase outbox processing (applies to every outbox handler, not just refunds)

**Tx-C (claim): short, on its own, committed before any business work.**

```sql
UPDATE outbox_event SET status='CLAIMED', lease_token=:new_token,
       lease_expires_at = now() + :lease, attempts = attempts + 1
WHERE id IN (SELECT id FROM outbox_event
             WHERE status='PENDING'
                OR (status='CLAIMED' AND lease_expires_at < now())
             ORDER BY id LIMIT :n FOR UPDATE SKIP LOCKED)
RETURNING id, lease_token;
```

Then COMMIT. Tx-C locks only outbox rows, never waits for them (`SKIP LOCKED`), and acquires nothing else.

**Tx-R (refund handler): one atomic transaction.** Locks are taken in the global order, and the outbox row is touched **last**:

| Step | Level | Action |
|---|---|---|
| 1 | 2 | Debit account `User FOR SHARE` |
| 2 | 5 | Wallet `FOR UPDATE` |
| 3 | 6 | Allowances `FOR UPDATE` |
| 4 | 7 | Request read |
| 5 | 8 | Get-or-verify the refund (§3), ledger, lines, audit, conditional notification (§3.3) |
| 6 | **9 (new)** | `UPDATE outbox_event SET status='DONE' WHERE id=:id AND lease_token=:token AND status='CLAIMED'`. **If 0 rows are updated, the lease was lost: raise, and the whole of Tx-R rolls back.** |
| 7 | — | COMMIT |

**Level 9** is added to the global order: "the transaction's own claimed outbox row, completion only". It is always the last lock taken.

**Retry behaviour:**

| Failure | What happens |
|---|---|
| Any failure in Tx-R | Full rollback. The event stays CLAIMED until its lease expires, then Tx-C claims it again. |
| Worker crash between Tx-C and Tx-R | The lease expires and the event is claimed again |
| Crash after Tx-R commits | The event is already DONE |
| `attempts` reaches its maximum | → `DEAD`, and an alert fires. **Financial events (`REQUEST_REFUND_DUE`) are never dropped.** `DEAD` needs operator action. |
| Account deletion | Cancels **notification-class** events only. **Financial events are never cancelled.** |

### 1.2 Why there can't be an outbox ↔ financial lock cycle

Only these transactions lock **existing** outbox rows:

| Transaction | Holds while touching outbox rows | Waits on |
|---|---|---|
| Tx-C (claim) | Nothing else | Nothing (`SKIP LOCKED`). So it has **no outgoing wait edges.** |
| Handler completion (level 9) | Levels 1–8 locks, already acquired | Its own single outbox row. It acquires **nothing after** that row, only commits. So once it holds an outbox row it has **no outgoing edges.** |
| Deletion's notification cancellation | Nothing else | Other outbox rows, in ID order |
| Retention purge | Nothing else | DONE / CANCELLED / DEAD rows, `SKIP LOCKED` |

Outbox **inserts** (level 8) create new rows. They take no locks on existing outbox rows, and OutboxEvent uses soft references (no FKs).

For a cycle, some transaction would have to hold an outbox row and then wait for a financial (or any other) lock. None of the transactions above does that. So no cycle can include an outbox row.

**Tests:**
- **T-CONC-033:** a handler holding wallet locks while another transaction claims or cancels events → no deadlock.
- **T-CONC-034:** the lease expires mid-handler and the event is claimed again → the old handler rolls back at step 6, and the new handler completes exactly once.
- **T-CONC-035:** a financial event survives deletion's event cancellation.

## 2. Crypto-shredding and backup restoration (amends v4.4 §1) [TR-23 revised, TR-24 new]

### 2.1 External compliance registry: authoritative even after a restore [TR-24]

**What it holds:** an append-only, hash-chained record of three entry types:
- `SHRED` (pseudonym, key_id, kek_version)
- `DELETION_COMPLETED` (account ID, deletion request ID, completed_at)
- `MAINTENANCE` (§5.4)

Each entry carries a monotonic `seq`, `prev_hash`, and an HMAC signature made with a registry key held in the deployment secret store.

**Where it lives:** **outside the primary database**, in a write-once storage location. The recommended option is a separate S3 bucket with Object Lock in compliance mode, versioning, and replication to a second region.
- The application role can only *put* objects. It can't delete or overwrite them.
- Only the restore role can read them.

**This is a new AWS resource, which may carry cost,** and is subject to the pending storage-provider decision (EP list) and your approval under `CLAUDE.md` §20. If you don't approve it, the alternative is a separate PostgreSQL instance with its own backup chain, append-only by trigger and privileges.

**The local table `ShreddedPseudonym`** in the primary database is a **cache** of the registry, not the authority.

**Write order (safe direction):**
1. Append the registry entry. It must be confirmed durable.
2. Then, in a database transaction, destroy the key, unlink the pseudonym, and insert into the cache.

If step 2 fails, a **reconciler** (hourly, and at startup) finds registry entries missing from the cache and re-applies them. Re-applying is idempotent. Shredding happens only at deletion PROCESSING, which is irreversible [DECIDED: completed deletion isn't reversed], so over-applying can never undo a valid decision.

**Restore procedure (fail-closed):**
1. Restore the database with **the application stopped**: Nginx serves a maintenance page, and the web and worker containers aren't started.
2. Fetch the full registry. Verify every signature and that the `seq` and `prev_hash` chain is unbroken. **Any gap or bad signature halts the restore.**
3. Re-apply every `DELETION_COMPLETED` entry newer than the backup by re-running the idempotent deletion steps. Then re-apply every `SHRED` entry.
4. Write `restore_reconciled_seq = <registry head>` into the database.
5. **Startup gate:** the application refuses to start (both web and workers) unless `restore_reconciled_seq` is at least the registry head it can read.
6. Start traffic.

**If the registry itself is unavailable:** the restore stops. The application doesn't start until the registry is recovered from a replica or a previous object version.

### 2.2 Key destruction and tombstones

`SubjectDataKey` columns: `key_id`, `pseudonym`, `kek_version`, `wrapped_key` (nullable), `created_at`, `destroyed_at`.

```sql
CHECK ((destroyed_at IS NULL) = (wrapped_key IS NOT NULL))
```

**Destruction** sets `wrapped_key = NULL` and `destroyed_at = now()` in one update. The remaining row is a **non-sensitive tombstone**: IDs and timestamps only, no key material. This table is a mutable mapping, not an append-only log.

**Making it irreversible, stated honestly.** Copies of the wrapped key can persist in old row versions until VACUUM runs, in archived WAL, and in backups. To make destruction truly irreversible:
- (a) The master key (KEK) is **versioned** and rotated monthly. New data keys are wrapped with the current version, and existing data keys are re-wrapped on rotation.
- (b) **Each KEK version is destroyed in the secret store once the longest backup or WAL retention that could hold keys it wrapped has passed.** After that, every old copy of a wrapped key is permanently undecryptable.
- (c) VACUUM runs on the key table after every destruction batch.

So the residual window is **at most the backup retention period** (AS-17, now explicitly bounded by KEK destruction). The retention period itself is part of the legal review (doc 13 OD-005).

### 2.3 Events involving several subjects: separate encrypted payloads per subject

- **Attribution rule:** each personal value belongs to exactly **one** subject. Request context (IP, user agent, location) belongs to the **actor**. Values about a target belong to the **target**.
- **Free-text personal content is banned** in log rows. Only reason codes and allowlisted structured fields are allowed.
- **Storage:** `enc_parts JSONB` holds an array of `{pseudonym, key_id, kek_version, nonce, ciphertext}`, **one envelope per subject**, each encrypted with that subject's data key (AEAD, with the event ID and pseudonym as associated data). A CHECK ensures there are no duplicate pseudonyms in the array (enforced by an insert trigger).
- **Shredding subject A** leaves A's envelope undecryptable, while B's envelope and the plaintext facts stay readable. The row itself is never modified.

### 2.4 Preventing identity reconstruction through linkable IDs

**Linkable-ID rule:** any identifier that could be joined to a retained record that identifies a person is stored **only inside the owning subject's envelope**, never in plaintext. This includes:
- `session_id`
- `authorization_id`
- IDs of person-owned resources (profile, request, connection, conversation, document)
- ledger `account_id`

Where a resource belongs to two subjects (a request between A and B), its ID goes in **both** subjects' envelopes.

**Plaintext is allowed for:** event facts, pseudonyms, `resource_type`, and `request_id`. `request_id` is random per request and only joins application logs, which hold pseudonyms only and are kept 30 days.

**Retained records at deletion PROCESSING:**

| Record | Treatment |
|---|---|
| `AuthSession` / `AuthToken` | **Deleted** (they're state, not logs) unless a hold applies |
| Authorizations, requests, connections, conversations (kept for the other participant, doc 03 §19) | Point to the **anonymised** User and profile rows, so no identifiers |
| Financial records under FR-DAT-009 | Keep `account_id` |

**Residual risks, disclosed:**
- (a) Identity can still be recovered **only** through records legally kept in identifiable form (financial or hold records). Those are accessible only to authorised roles, with every read audited. The logs add no extra path to them.
- (b) After unlinking, a pseudonym still groups that subject's past events together, which is pseudonymous behavioural data. Whether that's acceptable is added to the legal review (**R-19**).

## 3. Verifying refund idempotency (replaces v4.4 §2.2 step 3) [TR-15]

### 3.1 Get-or-verify

1. Run `INSERT … ON CONFLICT (account_id, idempotency_key) DO NOTHING RETURNING id`. **Inserted:** continue with a fresh refund as in v4.4 §2.2 steps 4–6.
2. **Not inserted:** `SELECT` the existing operation. This is a new statement under READ COMMITTED, so it sees the committed row that caused the conflict. **Verify all of the following**:

| # | Check |
|---|---|
| V1 | `op.account_id` = the request's debit account, and `op.kind = 'REFUND'` |
| V2 | Exactly one `CreditRefundOperation` with `refund_credit_operation_id = op.id`, `source_type = 'REQUEST_CANCELLATION'`, `request_id` = the expected request, `original_operation_id = request.debit_operation_id`, and the same account |
| V3 | Number of lines = number of the original operation's USAGE rows, with each USAGE row covered exactly once |
| V4 | Every REFUNDED line's refund ledger row exists with matching account, bucket, amount, `direction='CREDIT'`, `entry_type='REFUND'` and `operation_id = op.id` (re-checked defensively, even though FK-L1…L4 already guarantee it) |
| V5 | The request is CANCELLED, and its reason qualifies for a refund (OD-07) |

3. **All checks pass:** mark the outbox event DONE (level 9 lease check, §1.1) and COMMIT. No financial writes happen.
4. **Any check fails:** write **no** financial changes. In the same transaction:
   - insert `ReconciliationDiscrepancy(type=REFUND_INTEGRITY, request_id, details)`
   - set the outbox event to `BLOCKED_INTEGRITY` (never retried automatically)
   - commit and alert

   **No automatic repair.** Investigation and any correction go through the existing dual-approval adjustment process.

### 3.2 Updated T-CONC-030 / 031 and new tests

- **T-CONC-030** (amended): the second and later workers take the verify path and mark DONE only after V1–V5 pass.
- **T-CONC-036:** an existing operation with the wrong kind or account → `BLOCKED_INTEGRITY`, discrepancy raised, no ledger change.
- **T-CONC-037:** an existing operation with a missing line, injected by test-only SQL with the triggers disabled → `BLOCKED_INTEGRITY`.
- **T-CONC-038:** V5 fails (reason not refundable) → `BLOCKED_INTEGRITY`.

### 3.3 Notification consistency (fixes C-46) [REC-BIZ, OD-07f extended]

The refund transaction inserts the sender's "credit returned" outbox event **only if** the sender account is **ACTIVE**, meaning:
- not deactivated
- no deletion request in PENDING_RECOVERY, PROCESSING or COMPLETED
- no `LOGIN` or `FULL_ACCOUNT` restriction

Eligibility is read under the debit account's User `FOR SHARE` lock, so it's stable for the whole transaction. The delivery handler checks eligibility and preferences again at send time (v3).

**Ineligible senders:** no event is created, the refund is still recorded, and the refund is visible in their financial history if they later come back (deactivation or restriction lifted).

This replaces both v4.3's "notification after refund" and v4.4 §4.3's "no notification during deletion" with one rule.

## 4. DISPOSED wallets and late refunds (amends v4.4 §4) [TR-15; OD-07g stays OPEN]

### 4.1 Four separate steps

| Step | Who | What | When |
|---|---|---|---|
| **Record** the late refund | Refund transaction (§1, §3) | CreditOperation, CreditRefundOperation, lines, refund ledger rows (`post_closure=true`) | Always, for wallets in ACTIVE, CLOSED_RETAINED or DISPOSED |
| **Update** the projection | Same transaction | The purchased balance goes up. Allowance portions lapse because those allowances have expired. **The wallet status doesn't change.** | Same transaction |
| **Detect** the discrepancy | Nightly reconciliation | DISPOSED wallet with a balance above zero → `ReconciliationDiscrepancy(POST_DISPOSITION_CREDIT)`, plus an alert | Next run. **No automatic remediation.** |
| **Resolve** it | Finance, under dual approval | A new `DISPOSITION` operation applying **the approved OD-07g policy** → balance back to 0, discrepancy resolved with a reference to that operation | Manual |

### 4.2 Database rules

- The wallet CHECKs are **only** `purchased_* ≥ 0`. There's deliberately **no** CHECK tying DISPOSED to a zero balance.
- **The trigger on non-ACTIVE wallets** rejects new rows with `entry_type IN ('USAGE','GRANT','PURCHASE')`. It **allows** `REFUND` credits and `DISPOSITION` / `ADJUSTMENT` operations.
- CreditTransaction CHECK: `entry_type='DISPOSITION' ⇒ operation_kind='DISPOSITION' AND direction='DEBIT'`.
- **DISPOSED can't be reached until OD-07g is approved,** because a final disposition needs an approved policy. Until then, closed wallets stay `CLOSED_RETAINED`. The recommended default is still: **retain balances, no forfeiture until there's an approved policy** (OD-07g, OPEN).

### 4.3 Corrected T-DEL-010

**T-DEL-010:** with the wallet in DISPOSED, a late refund is processed.
- **The refund transaction succeeds:** ledger rows written, `post_closure=true`, projection increased, status still DISPOSED.
- The next reconciliation raises `POST_DISPOSITION_CREDIT`.
- **Reconciliation does no automatic remediation:** no ledger entry, no projection change, no status change by the reconciler.
- The balance stays until a dual-approved DISPOSITION operation resolves it (checked in T-DEL-012).

**T-DEL-012 (new):** a dual-approved DISPOSITION brings the balance to 0 and resolves the discrepancy. A single approval is rejected.

## 5. Partitioned append-only logs (amends v4.4 §1.5) [TR-23 revised]

### 5.1 Unique event IDs across partitions

PostgreSQL requires unique constraints on a partitioned table to include the partition key. So **the partition key is the ID itself:**
- `id` is a **UUIDv7**, which is time-ordered. It's generated by a database default function `uuid_v7()` (a small PL/pgSQL function, no new dependency; PostgreSQL 18 has it built in), so all IDs share the database server's clock.
- `audit_log` is `PARTITION BY RANGE (id)` with **`PRIMARY KEY (id)`**. That's valid because the key includes the partition column, and it **enforces uniqueness across all partitions.**
- Monthly partitions run `FOR VALUES FROM (uuid_v7_lower('2027-01-01')) TO (uuid_v7_lower('2027-02-01'))`. `occurred_at` stays a separate column.
- **There's no DEFAULT partition.** A job creates partitions 3 months ahead and alerts when less than 2 months are left. Inserting into a missing range fails, which is fail-closed.
- **The maintenance code refuses to create a partition for a past range,** so a range that has been dropped is never recreated.

`account_security_event` is built the same way.

### 5.2 Moving held events without duplicates

- **`audit_log_hold`:** a normal (unpartitioned) table with the same columns and `PRIMARY KEY (id)`.
- **`audit_log_hold_link`:** `(event_id, hold_case_id)` with `PRIMARY KEY (event_id, hold_case_id)`. One event can be under several holds **without being copied twice.**
- **Move and drop happen in one transaction** (plain `DETACH`, not `CONCURRENTLY`, so it can run inside a transaction):

```sql
BEGIN;
INSERT INTO audit_log_hold SELECT * FROM audit_log_2027_01
  WHERE <subject pseudonym in active holds> ON CONFLICT (id) DO NOTHING;
INSERT INTO audit_log_hold_link … ON CONFLICT DO NOTHING;
ALTER TABLE audit_log DETACH PARTITION audit_log_2027_01;
DROP TABLE audit_log_2027_01;
INSERT INTO maintenance_audit_log (…);  -- §5.3
COMMIT;
```

Every event exists in exactly one place before and after the commit, never both. A rerun after a failure is idempotent (`ON CONFLICT`), and a failure part-way leaves the partition untouched. Since past ranges are never recreated, an ID in the hold table can't reappear in the main table.

- **Reads** go through a view `audit_log_all` (`UNION ALL` of the two tables).
- **Releasing held rows (disclosed as a second, narrowly scoped removal path):** the security-definer function `release_held_events(hold_case_id)`, which only the maintenance role can run:
  - deletes the link rows for that hold
  - then deletes the hold-table rows that **have no remaining links and whose original retention has passed**
  - records the release in the maintenance log

  The application role still can't update or delete either table.

### 5.3 Maintenance audit records: kept beyond ordinary partitions

**`maintenance_audit_log`:** append-only (trigger plus privileges), **partitioned yearly by UUIDv7 ID**, and **contains no personal data or pseudonyms**. Columns:
- `id`, `op` (PARTITION_CREATE, PARTITION_DROP, HOLD_COPY, HOLD_RELEASE, SHRED_REAPPLY, RESTORE_RECONCILE)
- `target_table`, `partition_name`, `id_range_from`, `id_range_to`
- `row_count`, `held_row_count`, `ids_digest` (SHA-256 over the sorted dropped IDs)
- `hold_case_id`, `job_run_id`, `executed_by_role`, `approval_ref`
- `prev_hash`, `entry_hash` (a hash chain), `occurred_at`

**Every entry is also appended to the external compliance registry (§2.1) as a `MAINTENANCE` entry.**

**Retention:** a configurable long period (placeholder: 7 years, subject to legal review). When a yearly maintenance partition expires, dropping it is recorded **in the current year's partition and in the external registry**, so the record of maintenance never fully disappears. The hash chain shows whether any internal entry is missing.

**Auditability after ordinary partitions expire:** what remains is the maintenance log (ranges, counts, digests, hold copies) plus the external registry's independent, object-locked copy. Both survive any ordinary log partition's expiry, and the external copy survives database restores as well.
