## C11. Formal-request cancellation

**Current approved rules [DECIDED]:**
- `PENDING → CANCELLED` is an administrative action that needs a reason (doc 05 workflow; doc 15 §6).
- Administrative cancellation creates no cooldown by default (doc 05 rule 9; doc 03 M07).
- No refund on expiry (doc 05 rule 11).
- Refunds are compensating ledger entries, never deletions [DECIDED].

**Gap:** using CANCELLED for system triggers such as deletion, suspension, closure and block extends an admin-only status. That's a business change, so it sits in **OD-07** (revised below), not in a TR.

### 11.1 Model additions [TR]

New fields on `MatrimonialRequest`:
- `cancellation_reason` (enum below)
- `cancelled_by_type` (ADMIN | SYSTEM)
- `cancelled_by` (admin account, nullable)
- `cancellation_ref_type` and `cancellation_ref_id` (the triggering block, deletion request, moderation case or profile transition)
- `refund_outcome` (NOT_APPLICABLE | REFUNDED | PARTIALLY_LAPSED | LAPSED)

Constraint: `CHECK (status='CANCELLED') = (cancellation_reason IS NOT NULL)`.

### 11.2 Trigger table (every row except T1 is REC-BIZ under OD-07)

| # | Trigger | Actor | Request outcome | Reason code | Refund to sender's billing account | Cooldown |
|---|---|---|---|---|---|---|
| T1 | Admin cancellation for sender misconduct | Admin with `requests.cancel` + a moderation case reference | CANCELLED [DECIDED] | `ADMIN_SENDER_MISCONDUCT` | No | None [DECIDED default] |
| T2 | Admin cancellation for any other reason (error, support, recipient misconduct) | Admin with `requests.cancel` | CANCELLED [DECIDED] | `ADMIN_OTHER` | Yes | None [DECIDED default] |
| T3 | Recipient account deletion reaches **PROCESSING** | System | CANCELLED | `RECIPIENT_UNAVAILABLE` | Yes | None |
| T4 | Recipient profile **SUSPENDED** | System (fan-out after suspension) | CANCELLED | `RECIPIENT_UNAVAILABLE` | Yes | None |
| T5 | Recipient profile **CLOSED** | System | CANCELLED | `RECIPIENT_UNAVAILABLE` | Yes | None |
| T6 | **Recipient blocks sender** | System | CANCELLED | `RECIPIENT_UNAVAILABLE` | **Yes** (see contradiction C-17) | None. The block itself prevents new requests. |
| T7 | Sender account deletion reaches PROCESSING | System | CANCELLED | `SENDER_UNAVAILABLE` | No | None |
| T8 | Sender profile SUSPENDED | System | CANCELLED | `SENDER_UNAVAILABLE` | No | None |
| T9 | Sender profile CLOSED | System | CANCELLED | `SENDER_UNAVAILABLE` | No | None |
| T10 | Sender blocks recipient | System | CANCELLED | `SENDER_UNAVAILABLE` | No | None |
| — | Either party PAUSED, deactivated, in deletion **recovery**, or under a restrictive identity hold | — | **Not cancelled.** Frozen: both parties' actions are refused generically, and the expiry clock keeps running. | — | If it expires: no refund [DECIDED] | Expiry cooldown [DECIDED] |
| — | Hide My Profile From (either direction) | — | **Unchanged** [DECIDED: hide affects only new approaches] | — | — | — |
| — | Manager authorization revoked or paused | — | Unchanged. Requests belong to profiles. | — | — | — |

**Uniform reason codes.** The recipient-side triggers T3–T6 deliberately share one code, and the sender sees the same "No longer pending, credit returned" message for all of them. That way a refund pattern can't reveal a block, a suspension or a deletion [DECIDED: no disclosure of blocked relationships]. Internally, `cancellation_ref_type` records the real trigger, visible to admins only.

### 11.3 Refund mechanics [TR]

1. Each refund is one compensating `CREDIT/REFUND` ledger row per bucket debited by the original `operation_id`, returned to the **same bucket**, with idempotency key `refund:request:<id>`.
2. If the original allowance has EXPIRED, that portion **lapses** [REC-BIZ, OD-07]. No ledger amount is written for it; the lapse is recorded in AuditLog and `refund_outcome`. The purchased-bucket portion is always refundable, because purchased credits never expire [DECIDED].
3. Refunding into an EXHAUSTED but unexpired allowance makes it ACTIVE again (v4 §11.11).
4. Policy refunds happen automatically inside the cancelling transaction. They don't need the dual approval used for manual adjustments.

### 11.4 Records written for every cancellation [TR]

- `MatrimonialRequestHistory`: action CANCELLED, reason, actor type, actor, reference.
- `AuditLog`: always for T1 and T2, and for every refund or lapse.
- Ledger rows as in 11.3.
- Outbox notifications: the sender gets the uniform message; the recipient gets nothing for T3–T6.
- The linked interest stays `CONVERTED_TO_REQUEST` (C16).

**Fan-out:** T3–T5 and T7–T9 run as one transaction **per request** after the triggering transition commits (lock policy, C15). Until then, accepting is already impossible because eligibility is checked under a profile lock (C15, step 3).

**Tests:**
- T-REQ-030: each trigger produces the right reason, refund and cooldown.
- T-REQ-031: the sender-visible output for a block and a closure is identical.
- T-REQ-032: a mixed-bucket refund with one expired allowance gives PARTIALLY_LAPSED.
- T-REQ-033: a duplicate fan-out refunds once.
- T-REQ-034: accepting while the sender is suspended is refused.

## C12. COMPLETED → CLOSED

**Current approved rules [DECIDED]:** "COMPLETED is not reopened by default". Messaging requires an active connection.

**Recommendation [REC-BIZ, OD-06l]:** allow `COMPLETED → CLOSED`, but make the result **permanently non-reopenable**.

| Actor | Reason codes |
|---|---|
| Either party (owner, or a manager with `manage_connections` + step-up) | `PARTY_ENDED` |
| Moderation | `MODERATION` |
| Deletion processing | `ACCOUNT_DELETED` |
| Profile closure | `PROFILE_CLOSED` |

Each of these closes the connection.

**Why:** an engagement can end. Without this transition, completed partners would keep read-only access to each other's L2 profile and conversation indefinitely, and moderation and deletion would have no clean way to end that access.

**Model [TR]:** add `ProfileConnection.closed_from_status` (ACTIVE | PAUSED | COMPLETED). Reopening requires `closed_from_status ≠ COMPLETED` (C13).

**Alternative:** if you prefer COMPLETED to be terminal, deletion and moderation would remove access through the eligibility overlay without changing status, and parties couldn't end a completed connection themselves.

**Tests:** T-CON-040 (COMPLETED → CLOSED by each permitted actor), T-CON-041 (reopening a connection closed from COMPLETED is refused).

## C13. Reopening a CLOSED connection: strengthened checks

The flow uses `ConnectionReopenRequest`. Mutual confirmation [DECIDED] is necessary but never sufficient.

### 13.1 Checks at initiation **and again inside the confirming transaction** [TR, except where marked]

Each check is run for **both** profiles.

| # | Check | On failure |
|---|---|---|
| 1 | Acting-profile algorithm (v3 §9) with `manage_connections` (S tier, step-up) | 403 or 404 |
| 2 | Account active: not deactivated, no `LOGIN` or `FULL_ACCOUNT` restriction | Generic `reopen_not_available` |
| 3 | No deletion request in PENDING_RECOVERY or PROCESSING | Same |
| 4 | Profile status **ACTIVE**. PAUSED, SUSPENDED and CLOSED are all refused. | Same |
| 5 | Effective identity status APPROVED and no restrictive identity hold (v4 §11.2) | Same |
| 6 | No block in either direction | Same (no disclosure) |
| 7 | No `UserRestriction` on connections, messaging or interactions for either party | Same |
| 8 | `closed_from_status ≠ COMPLETED` (C12) | Same |
| 9 | Closure reason allows reopening: `PARTY_ENDED` only. `MODERATION`, `ACCOUNT_DELETED` and `PROFILE_CLOSED` can never be reopened by users [REC-BIZ, OD-06n]. | Same |
| 10 | Hide My Profile From: a party the other has hidden **can't initiate**, but the hider can [REC-BIZ, OD-06n] | Same |
| 11 | The other party has no live connection or pending request (the pair unique constraint is the backstop) | 409 generic |
| 12 | Within the request's time-to-live (suggested 14 days, configurable) [REC-BIZ, OD-06n] | `reopen_request_expired` |

**Lazy invalidation:** if any check fails at confirmation, the reopen request moves to `INVALIDATED` with an internal reason. Nothing is reopened.

### 13.2 Reopen-request states [TR]

PENDING → CONFIRMED | DECLINED | WITHDRAWN (by the initiator) | EXPIRED | INVALIDATED.

- A partial unique index allows only **one PENDING request per connection**.
- **Simultaneous initiation:** if the other party already has a PENDING request, creating one counts as **confirming** it. This happens under the pair lock.

**Effect of confirmation:**
- Connection → ACTIVE, with `closed_*` fields cleared and history written.
- The progress stage keeps its frozen value.
- The conversation becomes writable (it's derived).
- Both parties are notified.

**Tests:** T-CON-050…061, one per check, each checked at both initiation and confirmation. Plus a simultaneous initiation test (exactly one confirmation) and a suspension racing confirmation (refused).

## C14. `paused_by_profile` and concurrent pause/resume

### 14.1 Model [TR]

| Field | Purpose |
|---|---|
| `paused_by_profile` (FK to MatrimonialProfile, PROTECT, nullable) | The **party** is the profile, not the account. The owner or any manager with `manage_connections` acting for that profile can resume [REC-BIZ, OD-06h]. |
| `paused_at`, `pause_reason` (optional) | When and why |
| `paused_by_account` | **History only**: the actual actor |

Constraints:
- `CHECK ((status='PAUSED') = (paused_by_profile_id IS NOT NULL AND paused_at IS NOT NULL))`
- `CHECK (paused_by_profile_id IS NULL OR paused_by_profile_id IN (profile_one_id, profile_two_id))`

### 14.2 Behaviour, under pair lock → connection `FOR UPDATE`

| Operation | Precondition | Result |
|---|---|---|
| Pause by P | status ACTIVE | PAUSED, `paused_by_profile = P` |
| Pause by P when already PAUSED by P | — | 200, idempotent no-op |
| Pause by Q when already PAUSED by P | — | 409 `connection_already_paused`. `paused_by_profile` isn't changed. |
| Resume by P | status PAUSED, `paused_by_profile = P`, no block or restriction [DECIDED] | ACTIVE, pause fields cleared, history keeps who paused and who resumed |
| Resume by Q (the non-pauser) | — | 403 `action_not_allowed` |
| Close or complete while PAUSED | Per v4 §11.6 and C12 | Pause fields cleared, history kept |

**Concurrency:** two simultaneous pauses are serialised by the pair lock. The first one wins and the second gets 409 (or a no-op if it's the same party). A resume racing a close is also serialised, and the second operation sees the new state.

**Edge cases [REC-BIZ, OD-06h]:**
- If the pausing party's account is deactivated, the connection stays paused. The other party can't resume it, but can close it.
- If the pausing party's profile is closed or deleted, the connection is closed by that flow.

**Alternative (not recommended):** a "pause holds" model where both parties can hold a pause. It's fairer when both want a break, but more complex.

**Tests:** T-CON-070…076 (concurrent pauses, resume by the non-pauser, resume by a manager of the pausing profile, resume blocked by a block, invariant checks).

## C15. Lock-order cross-check and compliance matrix

### 15.1 Gaps found in v4 §12 (corrected here [TR-09 revised])

| ID | Gap | Fix |
|---|---|---|
| L-1 | **Refresh rotation** locked AuthToken then AuthSession. Deletion and revoke-all lock AuthSession then AuthToken, so the two could deadlock. | Refresh locks **AuthSession first**, then the parent AuthToken (TR-01 amended) |
| L-2 | Payment and subscription rows must be locked **before** the wallet, but v4 placed every "domain row" after allowances | Account-scoped financial rows move to step 2 |
| L-3 | **Accept versus suspension race:** eligibility was read without a lock | Pair-state services take `FOR SHARE` on both profile rows. Status changes take `FOR UPDATE`. |
| L-4 | The **interest daily cap** (OD-06g) is counted across pairs, so concurrent sends could exceed it | A per-sender-profile quota advisory lock |
| L-5 | **Block vs. message race:** messages didn't serialise with block or close | Messages take a **shared** pair advisory lock. Block and close take the exclusive lock. |
| L-6 | **View billing vs. block race** | View POST takes a shared pair lock before the wallet |
| L-7 | Block, hide and cooldown rows weren't in the type order | Added before Interest |
| L-8 | Deletion processing would lock the account (step 2) and then authorizations (step 1), which is backwards | Authorizations are revoked in **separate transactions**, one per authorization |

### 15.2 Revised global order (ADR-031). Never go backwards.

1. **Authorization row:** `FOR SHARE` for a delegated action, `FOR UPDATE` for pause, revoke or permission change.
2. **Account-scoped rows**, in this order: AccountDeletionRequest → User → UserSubscription → SubscriptionBillingPeriod → Payment / RefundRequest / AdjustmentRequest → AuthSession → AuthToken.
3. **Profile-scoped:** MatrimonialProfile rows, ascending ID (`FOR SHARE` to read status for pair operations, `FOR UPDATE` for status changes). Then profile quota advisory locks, ascending.
4. **Pair advisory locks:** exclusive for state changes, shared for messaging, document access and view billing. Ascending key.
5. **Billing wallet** `FOR UPDATE` (only one per transaction).
6. **Allowances**, ordered by `expires_at, id`.
7. **Pair and domain rows**, in this type order: ProfileBlock → HiddenProfile → DirectionalCooldown → Interest → MatrimonialRequest → ProfileConnection → ConnectionReopenRequest → RelationshipProgress → Conversation / Message / DocumentPermission. Within each type, ascending ID.
8. **Inserts only:** history, ledger, audit, outbox, security events.

**Unchanged rules:**
- One aggregate per transaction for bulk jobs and fan-out.
- No external calls inside a transaction.
- Retry on deadlock (40P01), serialization failure (40001) and lock-not-available (55P03), up to 3 attempts, then 503.

### 15.3 Enforcement [TR, new TR-22]

- Each service declares a `LOCK_PLAN`.
- In test and debug settings, a lock-acquisition tracker raises an error on any out-of-order acquisition.
- T-LOCK-004 runs every service in the matrix under that tracker.

## C16. Interest lifecycle: unambiguous expiry and transitions

### 16.1 Expiry fields [TR]

- `expires_at` is set **once, at creation**: `sent_at + configured period` if OD-06e is approved, otherwise NULL.
- It's immutable. A later change to the configured period affects only new interests. Whether existing interests become expirable if OD-06e is approved later is **REC-BIZ, OD-06e: no retroactive expiry**.
- **Expiry applies only to status PENDING.**
- **Liveness predicate:** `(status='PENDING' AND (expires_at IS NULL OR expires_at > now)) OR status='RECIPROCATED'`.
- The worker and lazy paths both use `expire_if_due` (v4 §7 C).

### 16.2 State table

| State | Live? | Expires? | Allowed exits | Cooldown on entry | Counterparty sees |
|---|---|---|---|---|---|
| PENDING | Yes, until `expires_at` | Yes (if OD-06e) | → RECIPROCATED, CONVERTED_TO_REQUEST, DECLINED, WITHDRAWN, EXPIRED, CLOSED | — | Pending |
| RECIPROCATED | Yes | **Never** | → CONVERTED_TO_REQUEST (either party, OD-06c), **WITHDRAWN (either party, OD-06m)**, CLOSED | — | Mutual interest |
| CONVERTED_TO_REQUEST | No (terminal) | — | None. The request's lifecycle takes over, and request outcomes never change the interest. | Per request outcome [DECIDED] | Request status |
| DECLINED | No (terminal) | — | None | **30 days, sender → receiver [DECIDED]** | Declined |
| WITHDRAWN | No (terminal) | — | None | None (OD-06d) | "No longer pending" |
| EXPIRED | No (terminal) | — | None | None. Either party may send a new interest immediately. | "No longer pending" |
| CLOSED | No (terminal) | — | None. Unblocking doesn't revive it. | None | "No longer pending" |

**Closure reasons** (v4.1): `BLOCKED`, `PROFILE_CLOSED`, `ACCOUNT_DELETED`, `ADMIN`. `SUPERSEDED_BY_REQUEST` is removed (contradiction C-21).

### 16.3 Rules for actions on stale or frozen interests [TR unless marked]

1. **Every action** on an interest (reciprocate, decline, withdraw, convert, auto-reciprocate) runs lazy expiry under the pair lock first. If the interest is now EXPIRED, the action fails with `interest_not_pending`, and nothing is charged.
2. **Auto-reciprocation (OD-06a)** when the reverse interest is logically expired: the reverse row is expired first, then a new forward PENDING row is created. Auto-reciprocation doesn't count toward the daily cap [REC-BIZ, OD-06g].
3. **A request created while an interest is live always converts and links that interest.** If OD-06b is rejected, the original sender's direct request is refused with `interest_pending` until they withdraw the interest or it expires. There's no unlinked "superseded" path.
4. **Frozen** (either party PAUSED, SUSPENDED, deactivated, in deletion recovery, or under a restrictive identity hold): the status doesn't change, actions by **both** parties are refused generically, and **the expiry clock keeps running** [REC-BIZ, OD-06f].
5. **Hide** (either direction): unchanged [DECIDED].
6. **Block, closure, deletion processing:** a live interest (PENDING or RECIPROCATED) → CLOSED with the matching reason, in the triggering transaction or its per-pair fan-out [REC-BIZ, OD-06f].
7. **Uniqueness:** the partial unique index on `status IN ('PENDING','RECIPROCATED')` is resolved by lazy expiry before any insert. RECIPROCATED rows never go stale.

**Tests:**
- T-INT-021…030: every action on a logically expired row; expiry while frozen.
- RECIPROCATED never expires; withdrawal from RECIPROCATED by either party.
- No retroactive expiry.
- Request outcomes leave CONVERTED unchanged.
- The `SUPERSEDED_BY_REQUEST` value no longer exists.
