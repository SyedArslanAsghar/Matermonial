## 1. F2: append-only logs and deletion anonymisation (revises TR-23)

### 1.1 Correction first: OutboxEvent isn't an append-only log (C-35)

v4.3 listed OutboxEvent alongside AuditLog and AccountSecurityEvent as append-only. That was wrong. OutboxEvent is a **work queue**: rows are claimed, retried and marked done (v3 TR-11, SKIP LOCKED). So it's handled differently:

| Aspect | OutboxEvent rule [TR] |
|---|---|
| Payload | Event type plus **identifiers only** (aggregate ID, recipient user ID). No names, phones, message text or other personal content. Handlers load data when they deliver and re-check eligibility (v3). |
| Changes allowed | Status, attempt count, lease and error fields are updatable. The payload and identifiers are immutable (a column-level trigger). |
| On account deletion | Deletion processing **cancels** that account's undelivered events (status CANCELLED). |
| Retention | Delivered or cancelled rows are purged after 30 days (configurable) by the retention job |
| Anonymisation | Not needed beyond the above. Payloads hold no direct identifiers and the rows are short-lived. |

**Only AuditLog and AccountSecurityEvent are append-only logs.** The rest of this section applies to them.

### 1.2 What goes directly into an append-only event row [TR]

| Category | Fields | How it's stored |
|---|---|---|
| Event facts (not personal) | `id`, `event_type` / `action`, `result`, `reason_code`, `actor_type`, `resource_type`, `occurred_at`, `request_id`, `authorization_id`, `session_id` (a random UUID) | Plaintext, forever immutable |
| Subject and actor references | `subject_pseudonym`, `actor_pseudonym`, `represented_profile_pseudonym` | **Random pseudonym UUIDs.** Never the `user_id` or `profile_id` themselves. |
| Personal context | `ip_address`, `user_agent`, `approximate_location`, personal metadata values | **Encrypted** with the subject's data key (`enc_payload`, AEAD, plus `key_id`) |
| Anonymous failed logins | `subject_hash` (keyed HMAC of the phone) | Plaintext hash. Short retention (90 days), and the HMAC key rotates on the same cycle. |

**No direct identifiers** (phone, email, name, document numbers) are ever written into a log row.

### 1.3 How the identity mapping is kept [TR]

Two **mutable** tables. They're mappings, not logs. Access is restricted to the security admin role, and every read is audited.

**`SubjectPseudonym`:**
- `pseudonym` (PK, random UUID)
- `subject_type` (ACCOUNT | PROFILE)
- `subject_id` (nullable)
- `created_at`, `unlinked_at`, `hold_ref` (nullable)
- One pseudonym per subject, created when the subject's first event is logged.

**`SubjectDataKey`:**
- `key_id`, `pseudonym`
- `wrapped_key` (the data key, encrypted with a master key held in the deployment secret store, envelope-style)
- `created_at`, `destroyed_at`

**Reading events:**
- **The user's own history (FR-007):** subject → pseudonym → events → decrypt with the subject's key.
- **Security investigations:** the same path, under role permission and with the read audited.

### 1.4 How anonymisation works without touching the logs [TR]

At the deletion PROCESSING step (in its own fan-out transaction, one per subject):
1. **Unlink:** set `SubjectPseudonym.subject_id = NULL` and `unlinked_at = now`.
2. **Crypto-shred:** delete the `SubjectDataKey` row (keeping a `destroyed_at` marker row).
3. Append the pseudonym to the **shred list** (an append-only `ShreddedPseudonym` table), used to redo the shredding after a backup restore.

**Result:** every existing log row stays **byte-for-byte unchanged**. No UPDATE or DELETE happens on AuditLog or AccountSecurityEvent. But those rows can no longer be linked to the person: the pseudonym has no subject, and the encrypted personal context can't be decrypted. The append-only rule isn't weakened.

**Retained financial records** (ledger, ProfileView) keep their `account_id`. They point at the retained, anonymised User row (doc 03 §19: anonymise identifiers). They aren't log rows, and they fall under the financial-retention rule [FR-DAT-009].

### 1.5 Retention and legal or security requirements [TR; periods subject to doc 13 OD-005]

| Mechanism | Rule |
|---|---|
| **Legal or security hold** (FR-DAT-009) | If an active hold covers the subject, steps 1–3 of §1.4 are **deferred**. `hold_ref` is set and the event is audited. They run when the hold is released. |
| **End of retention** | The logs are **range-partitioned by month**. When a partition is past its category's retention period and contains no held subject, a privileged maintenance role **drops the whole partition** (DDL, run by a scheduled job). The drop itself is recorded in AuditLog, in the current partition. |
| **Held subjects in an expiring partition** | Their rows are copied into a hold partition (an INSERT, which is append-only compatible) before the old partition is dropped |
| **Is that a weakening of append-only?** | **Stated openly:** the application role has no UPDATE or DELETE rights (triggers plus privileges). The only way rows ever leave is the **whole-partition drop at the end of retention**, by the maintenance role, audited. No selective deletion or modification of individual rows exists. |
| **Backups** | Backups contain keys until the backups themselves expire (per backup policy). On any restore, the shred list is re-applied before the system serves traffic (AS-17). |

**Tests:**
- T-SEC-007: after anonymisation, the log rows' content hashes are unchanged, the subject can't be resolved, and decryption fails.
- T-SEC-008: UPDATE and DELETE are still rejected for the application role.
- T-SEC-009: only the maintenance role can drop a partition, and the drop is audited.
- T-SEC-010: an active hold defers anonymisation.
- T-SEC-011: a backup restore re-applies the shred list.
- T-SEC-012: no direct identifier appears in log rows (schema test).

## 2. Refund CreditOperation idempotency and atomicity (amends v4.3 §2.3 and §5)

### 2.1 Deterministic key [TR]

The refund `CreditOperation` uses **`idempotency_key = 'refund:request:<request_id>'`**, under the existing `UNIQUE (account_id, idempotency_key)`. `CreditRefundOperation` keeps `UNIQUE (source_type, request_id)` as a second guard.

### 2.2 One atomic transaction (replaces v4.3 §2.3 steps 8–9)

Everything happens in **a single database transaction**. Nothing outside it (no external calls). There's **no `try/except IntegrityError` inside it**, because that would abort the PostgreSQL transaction or need savepoints. Conflicts are handled with `ON CONFLICT`.

1. Claim the outbox event: `UPDATE outbox … WHERE id=? AND status='CLAIMED' AND lease_token=?`. If no row matches, the lease was lost: roll back and exit.
2. Debit account User `FOR SHARE` → wallet `FOR UPDATE` → allowances `FOR UPDATE`. The wallet lock serialises concurrent workers.
3. `INSERT INTO credit_operation (…, kind='REFUND', idempotency_key='refund:request:<id>') ON CONFLICT (account_id, idempotency_key) DO NOTHING RETURNING id`.
   - **No row returned:** the refund was completed by a transaction that has already committed. A transaction that's still running would have made this insert wait, and one that rolled back would leave no conflict. Mark the outbox event DONE, commit, and exit. Nothing else is written.
4. Insert `CreditRefundOperation` (a conflict here is impossible after step 3; if it ever happens, it's an error and everything rolls back).
5. For each debit row: insert the refund `CreditTransaction` (REFUNDED lines), update the projection, insert the `CreditRefundLine`.
6. Insert AuditLog, then the OutboxEvent for the sender's notification.
7. Mark the claimed outbox event DONE.
8. Commit. **The deferred constraint triggers run here** (§3.3): completeness, and exactly one CreditRefundOperation per REFUND operation.

**Any failure in steps 3–8 rolls back everything,** including the CreditOperation header and the outbox completion. So an orphan header or a partial financial record **can't survive a commit**. The event is then redelivered once the lease expires.

**A fully lapsed refund** (every line LAPSED) still commits the header, the CreditRefundOperation and the lines, with no ledger amount rows. That permanently records that the refund was evaluated.

### 2.3 Updated tests

| ID | Scenario | Pass condition |
|---|---|---|
| **T-CONC-030** (updated) | 10 workers process the same `REQUEST_REFUND_DUE` at the same time, including two holding stale leases | Exactly 1 CreditOperation (`refund:request:<id>`), 1 CreditRefundOperation, lines = debit rows, 1 refund ledger row per REFUNDED line, projection = Σ ledger. Stale-lease workers write nothing. No errors leak out. |
| **T-CONC-031** (updated) | A failure is injected **at each step**: after step 3, 4, 5 (each line), 6 and 7; and at commit, by forcing the deferred trigger to fail | After each failure: no CreditOperation, CreditRefundOperation, line, ledger row or projection change remains, and the outbox event is still pending. The rerun succeeds exactly once. A crash **after** commit causes a rerun that's a no-op. |
| T-CONC-032 (new) | A refund running at the same moment as a different operation on the same wallet | Serialised by the wallet lock. Both are correct. |

## 3. Corrected composite-FK targets (replaces v4.3 §5.1–5.2 structure)

### 3.1 Columns and unique keys [TR]

**`CreditOperation`:**
- `id` (PK), `account_id`, `kind` (DEBIT | GRANT | PURCHASE | EXPIRY | REFUND | ADJUSTMENT | DISPOSITION), `idempotency_key`
- **`UNIQUE (id, account_id, kind)`** (FK target **UK-OP**)
- `UNIQUE (account_id, idempotency_key)`

**`CreditTransaction`:**
- `id` (PK), `account_id`, `operation_id`, `operation_kind`
- `bucket`, `allowance_id` (nullable)
- `amount` (> 0), `direction` (DEBIT | CREDIT), `entry_type` (USAGE | GRANT | PURCHASE | EXPIRY | REFUND | ADJUSTMENT | DISPOSITION)
- `refund_operation_id` (nullable), `bucket_balance_after`
- **FK (operation_id, account_id, operation_kind) → CreditOperation (id, account_id, kind)** [UK-OP]
- **`UNIQUE (id, account_id, operation_id, bucket, amount, direction, entry_type)`** (FK target **UK-CT**)
- CHECKs:
  - `entry_type='USAGE' ⇒ direction='DEBIT' AND operation_kind='DEBIT'`
  - `entry_type='REFUND' ⇒ direction='CREDIT' AND operation_kind='REFUND' AND refund_operation_id IS NOT NULL`
  - `(bucket LIKE 'ALLOWANCE_%') = (allowance_id IS NOT NULL)`

**`CreditRefundOperation`:**
- `id`, `account_id`, `source_type`, `request_id`
- `original_operation_id`, `original_kind` (CHECK `= 'DEBIT'`)
- `refund_credit_operation_id`, `refund_kind` (CHECK `= 'REFUND'`)
- **FK (original_operation_id, account_id, original_kind) → CreditOperation (id, account_id, kind)** [UK-OP]
- **FK (refund_credit_operation_id, account_id, refund_kind) → CreditOperation (id, account_id, kind)** [UK-OP]. This puts "the refund operation's kind is REFUND" in a database FK. In v4.3 it was a trigger.
- **FK (request_id, original_operation_id) → MatrimonialRequest (id, debit_operation_id)** (requires `UNIQUE (id, debit_operation_id)` on the request)
- `UNIQUE (source_type, request_id)`
- `UNIQUE (refund_credit_operation_id)`
- **`UNIQUE (id, account_id, original_operation_id)`** (target **UK-RO1**)
- **`UNIQUE (id, refund_credit_operation_id)`** (target **UK-RO2**)

**`CreditRefundLine`** (all ordinary columns):

| Column group | Columns | Nullability |
|---|---|---|
| Parent | `refund_operation_id`, `account_id`, `original_operation_id` | Always NOT NULL |
| Original debit | `original_transaction_id`, `original_bucket`, `original_amount`, `original_direction` (CHECK `'DEBIT'`), `original_entry_type` (CHECK `'USAGE'`) | Always NOT NULL |
| Disposition | `disposition` (REFUNDED \| LAPSED) | NOT NULL |
| Refund side | `refund_transaction_id`, `refund_account_id`, `refund_credit_operation_id`, `refund_bucket`, `refund_amount`, `refund_direction`, `refund_entry_type` | **All NULL** when LAPSED, **all NOT NULL** when REFUNDED |

### 3.2 Matching foreign keys

Each FK's column list matches its target unique key exactly, column for column.

| FK | Referencing columns (CreditRefundLine) | Target | Match | Purpose |
|---|---|---|---|---|
| FK-L1 | (original_transaction_id, account_id, original_operation_id, original_bucket, original_amount, original_direction, original_entry_type) | CreditTransaction **UK-CT** (id, account_id, operation_id, bucket, amount, direction, entry_type) | FULL (all NOT NULL) | The original is a USAGE debit, of this account, in this operation, in this bucket, for this amount |
| FK-L2 | (refund_transaction_id, refund_account_id, refund_credit_operation_id, refund_bucket, refund_amount, refund_direction, refund_entry_type) | CreditTransaction **UK-CT** | **FULL**: all NULL (LAPSED) or all checked (REFUNDED). A partly filled row is rejected. | The refund row is a CREDIT/REFUND in the refund operation, with matching account, bucket and amount |
| FK-L3 | (refund_operation_id, account_id, original_operation_id) | CreditRefundOperation **UK-RO1** | FULL | The line belongs to a parent with the same account and original operation |
| FK-L4 | (refund_operation_id, refund_credit_operation_id) | CreditRefundOperation **UK-RO2** | SIMPLE (skipped only when `refund_credit_operation_id` is NULL, which a CHECK allows only for LAPSED) | The refund row's operation is the parent's REFUND operation |

**CHECKs on the line:**
- `disposition='LAPSED' ⇒` all seven refund-side columns are NULL.
- `disposition='REFUNDED' ⇒` all seven are NOT NULL **and** `refund_account_id = account_id`, `refund_bucket = original_bucket`, `refund_amount = original_amount`, `refund_direction = 'CREDIT'`, `refund_entry_type = 'REFUND'`.
- `UNIQUE (original_transaction_id)`, `UNIQUE (refund_transaction_id)`.

**How the chain proves the refund row belongs to a REFUND operation with direction CREDIT:**
1. FK-L2 forces the refund transaction to have `entry_type = 'REFUND'`, `direction = 'CREDIT'`, and `operation_id = refund_credit_operation_id`.
2. The CreditTransaction CHECK forces `operation_kind = 'REFUND'`, and its FK to UK-OP makes that kind real.
3. FK-L4 and the parent's FK to UK-OP tie that operation to the parent's REFUND operation.

All of this is enforced by database constraints.

### 3.3 Where each rule is enforced

| Layer | Rules |
|---|---|
| **Database constraints** (unique, FK, CHECK) | Account equality. Original-operation equality. Bucket equality. Amount equality (stricter than ≤). Debit is USAGE/DEBIT. Refund is CREDIT/REFUND in a REFUND-kind operation. Each debit row refunded at most once. Each refund row used once. One refund per request. Request ↔ debit operation link. All-or-nothing refund-side columns. |
| **Triggers** | (a) `BEFORE INSERT` on the line: original and refund `allowance_id` must be equal (`IS NOT DISTINCT FROM`). This can't be a composite FK because `allowance_id` is NULL for purchased buckets. (b) `DEFERRABLE INITIALLY DEFERRED` at commit: line count = number of the original operation's USAGE rows. Every REFUND CreditOperation has exactly one CreditRefundOperation. (c) `BEFORE UPDATE OR DELETE` rejects every change on CreditOperation, CreditTransaction, CreditRefundOperation and CreditRefundLine. |
| **Service validation, transactional** | Whether the cancellation reason qualifies for a refund (OD-07). The lapse decision (allowance EXPIRED, read under the allowance lock). Lock order. Projection update. Building lines from the full debit set. Outbox lease handling. |
| **Nightly reconciliation** | Projection = Σ ledger. Every qualifying CANCELLED request has a refund operation. Post-closure credits (§4). |

**Tests:** T-REQ-039…046 rewritten against FK-L1…L4 and the CHECKs, including a partly filled refund side rejected by MATCH FULL, a refund row in a non-REFUND operation rejected, and wrong direction or entry type rejected. Plus T-REQ-050 (allowance-mismatch trigger) and T-REQ-051 (deferred one-parent-per-REFUND-operation trigger).

## 4. Refunds arriving during or after deletion PROCESSING

### 4.1 What's approved today

| Rule | Status |
|---|---|
| The ledger is permanent and history is never deleted | [DECIDED] |
| Balances never go negative | [DECIDED] |
| Purchased credits don't expire | [DECIDED] |
| Financial records retained under FR-DAT-009 | [DECIDED] |
| Doc 05 rule 13: "purchased credit and refund treatment follows the published policy" | That published policy **doesn't exist** (C-38) |

What finally happens to remaining credits at deletion (kept, paid out or forfeited) is therefore a **business decision**. It's proposed as **OD-07g**, not invented here.

### 4.2 Deletion financial step [TR, mechanics only]

This is a fan-out transaction, run after the account is in PROCESSING:
1. User `FOR SHARE` → wallet `FOR UPDATE` → allowances `FOR UPDATE`.
2. Every active allowance → EXPIRED, with EXPIRY ledger entries for any remainder [DECIDED: allowances expire]. Refunds to those allowances later **lapse** (OD-07d).
3. **The wallet becomes `CLOSED_RETAINED`.** The remaining purchased balance stays on the projection as a **recorded, unusable balance**. No ledger entry zeroes it, so no forfeiture is implied.
4. Record `closed_at` and `closure_operation_ref`.

New wallet columns: `status` (ACTIVE | CLOSED_RETAINED | DISPOSED) and `closed_at`. Usage (DEBIT/USAGE) on a non-ACTIVE wallet is rejected by the service and by a trigger.

### 4.3 A late refund (arriving after step 4.2)

The refund transaction (§2.2) runs **unchanged**:
- It's always recorded against the **original debit account**: CreditOperation, CreditRefundOperation, lines and ledger rows.
- Purchased-bucket portions **increase the retained balance** of the `CLOSED_RETAINED` wallet.
- Allowance portions lapse (the allowances have expired).
- Each refund row gets `post_closure = true` (a column set at insert, never updated).
- The sender gets no notification, because the account is being deleted.

**Nothing is discarded.**

**If the final disposition has already been carried out** (the wallet is `DISPOSED`, per whatever policy OD-07g approves):
- The late refund is still recorded the same way, and the balance becomes greater than zero.
- Nightly reconciliation flags a `POST_DISPOSITION_CREDIT` discrepancy.
- Finance applies the same approved policy through a new **DISPOSITION** operation under dual approval.
- **Nothing happens automatically** (the v3 rule: no auto-fix).

### 4.4 Reconciliation

The nightly job checks that:
- (a) the closed wallet's projection = Σ ledger
- (b) every `post_closure` credit is listed in the finance report for that account
- (c) every DISPOSED wallet has a zero balance, or an open discrepancy

Any discrepancy goes into `ReconciliationDiscrepancy`, triggers an alert, and is corrected only by a compensating entry under dual approval.

### 4.5 Business decision [OD-07g, OPEN; REC-BIZ default]

| Option | Description |
|---|---|
| **Recommended default** | Keep the remaining purchased balance (including late refunds) as a recorded balance on the closed account until a published credit-and-refund policy and legal review decide the final treatment. **No forfeiture without your approval.** |
| Alternatives | Pay out on request within a defined period, or forfeit after a published notice period |

**Warning:** forfeiture would have to be squared with the [DECIDED] rule that purchased credits don't expire. I'm flagging that, not resolving it.

**Tests:**
- T-DEL-007: refund before the financial step → disposed by the step.
- T-DEL-008: refund after the financial step → recorded, retained balance increases, `post_closure=true`.
- T-DEL-009: refund to an expired allowance → lapses.
- T-DEL-010: refund after DISPOSED → discrepancy raised, nothing changed automatically.
- T-DEL-011: usage on a closed wallet is rejected.

## 5. Bounding the whole GET snapshot (replaces the v4.3 §4 bound)

**Correction (C-37):** `statement_timeout` limits each SQL statement separately, not the whole multi-statement transaction. v4.3 got that wrong.

### 5.1 Request deadline [TR; refines TR-19]

- **Deadline D = request start + 3 s** (configurable, `PROFILE_DETAIL_DEADLINE_MS`), set when the view starts.
- The GET opens one `READ ONLY, REPEATABLE READ` transaction.
- A Django `execute_wrapper` around that transaction does this **before every statement**:
  - computes the remaining time `r = D − now`
  - if `r ≤ 0`, raises `DeadlineExceeded`
  - otherwise runs `SET LOCAL statement_timeout = min(r, 5000 ms)`

  So no statement can run past D. **The 5-second `statement_timeout` stays as the per-query safeguard.**
- The response body is **built entirely in memory inside the transaction**. After the last read, the deadline is checked once more. Only then does the read-only transaction commit and the response go out.
- **Backstops** for stalls in application code between statements: `idle_in_transaction_session_timeout = 5 s` on this connection, and the web server worker timeout. If PostgreSQL ≥ 17 is used, `SET LOCAL transaction_timeout = D` is added as a further backstop (optional; AS-18, since AS-3 only assumes ≥ 15).

### 5.2 When the deadline is exceeded

- Any `DeadlineExceeded`, `statement_timeout` cancellation (57014), idle-transaction termination or connection loss → **roll back**.
- Return **`503 request_deadline_exceeded`** with `Retry-After`, an error envelope, and **no profile data at all**. Any partly built body is thrown away.
- Nothing is written (it was read-only). Nothing is charged.
- The event is logged with the `request_id` and counted in a metric.

### 5.3 Guarantee (replaces v4.3)

Each successful response comes from one consistent snapshot. **The snapshot is never more than D old when the response is released** (plus network transfer time). Changes that commit before the snapshot is taken are always honoured. A request that can't finish within D returns nothing.

**Tests:**
- T-MAT-023: a delay injected between statements past D → 503, no data.
- T-MAT-024: a slow single statement → cancelled by the per-statement limit derived from D → 503.
- T-MAT-025: deadline passed after the body is built but before release → 503.
- T-MAT-026: normal requests still meet D.
- T-CONC-060/061 still apply.
