**Rule:** the dimensions are independent. None of them may stand in for another. An APPROVED document can contain PROPOSED requirements. An APPROVED requirement can be NOT_STARTED. No implementation status can move past PLANNED unless its requirement is APPROVED.

**Assigners:**
- **Owner:** you.
- **Technical approver:** you, or someone you name in doc 19.
- **Reviewer:** a human code reviewer you name. Until you name one, that's you.
- **Claude:** Claude Code.

These are two independent concepts in two independent fields (state machines in §11.6 and §11.7):
- **Connection lifecycle** says whether the relationship channel exists and what it allows. It controls access level L3, messaging and reopening.
- **Progress stage** is a shared, descriptive label for how far discussions have got. It never grants or removes access.

**Coupling rules:**
- The stage can only be changed while the connection is **ACTIVE**. It's frozen while the connection is PAUSED, COMPLETED or CLOSED. History is kept.
- Progress responses show "Closed" whenever the connection is CLOSED. That keeps FR-CON-004's user-visible list while storing nothing (DCR-37; confirmation in OD-06i).
- Reaching ENGAGED doesn't complete the connection. Completing a connection doesn't change the stage (REC-BIZ, OD-06i).
- `RelationshipProgress.status` is renamed `stage`, and `CLOSED` is removed from its choices. `ProfileConnection.status` is unchanged.

### C. Stale interest and request rows (C4-C; TR-18)

**Shared function:** `expire_if_due(row, now)`. It's the **only** code that moves a PENDING interest or request to EXPIRED. It does all of the following in one step:
- a conditional `UPDATE … SET status='EXPIRED' WHERE id=? AND status='PENDING' AND expires_at <= now`
- if exactly one row changed, it writes the history row (actor SYSTEM, `trigger` = WORKER or LAZY)
- for **requests**, it creates the `DirectionalCooldown` with `starts_at = expires_at` (the logical expiry time, not now) and `ends_at = expires_at + 30×24h` [DECIDED cooldown; TR timing]
- it writes the outbox event (expiry notification)

If zero rows changed, it does nothing, so it's idempotent.

**Create-interest and create-request service, in one transaction (READ COMMITTED):**
1. Run the acting-profile algorithm (v3 §9). For a delegated write, take `FOR SHARE` on the authorization row.
2. **Take the pair advisory lock:** `pg_advisory_xact_lock(NS_PAIR, hash(least_id ‖ greatest_id))`.
3. **Re-read after the lock.** Each statement gets a fresh snapshot under READ COMMITTED, so this sees everything committed by whoever held the lock before. Select every interest and request for the pair with status ∈ {PENDING, RECIPROCATED} `FOR UPDATE`.
4. Call `expire_if_due` on each row whose `expires_at <= now`. Interests only do this if OD-06e is approved; otherwise interests have `expires_at` NULL. RECIPROCATED doesn't expire (REC-BIZ, OD-06e).
5. Check the cooldown, including any cooldown just created in step 4. Then apply the remaining rules (live request in either direction, connection, block, hide, eligibility).
6. Create the new row, or convert the live interest (§12 conversion). The partial unique indexes are the backstop: if one fires, it means a lock was skipped (a bug), and the result is a generic 409, never a duplicate.
7. Write history, audit and outbox. Commit.

**Under concurrency:**

| Case | Behaviour |
|---|---|
| Two creates for the same pair | Serialised by the advisory lock. The second one sees the first's row in step 3 and is rejected generically. |
| Worker vs create | The worker also takes the pair lock before calling `expire_if_due`, so only one of them performs the transition. The other sees EXPIRED, or zero rows updated. Exactly one history row, one cooldown and one notification. |
| Read paths (lists, detail) | Never write. They apply the row 21 liveness predicate, so a logically expired row shows as expired before the worker gets to it. |
| Unrelated pairs | Never contend |

**Must use READ COMMITTED.** Under REPEATABLE READ, the snapshot would be taken before the lock and could miss rows.

## 8. Profile-Detail Access: Revalidation vs Billing (C5; TR-19)

**Principle:** authorization decides *whether* someone can see something. Billing only decides *whether a view must have been paid for*. A paid grant is never permanent access.

`GET /profiles/{id}/` runs these steps on **every** request and writes **no** billing, ledger, ProfileView or VisitorHistory rows:
1. The acting-profile algorithm (v3 §9) with `view_profile_details` (or `view_profile` for the owner's own profile).
2. Load the target. If it's absent, CLOSED, or its owner's deletion is in progress or recovery: generic 404 (§9 lifecycle overlay).
3. **Blocks in both directions:** a block either way → 404.
4. **Hide My Profile From:** if the target hid the viewer → 404, unless an L3 connection or an existing pending item exists (§9).
5. **Restrictions:** a viewer account or profile restriction, or a target restriction or suspension → 404 or 403 per the restriction type, generic.
6. **Connection status:** ACTIVE → L3. PAUSED or COMPLETED → L2 + read-only history. CLOSED → treated as unrelated, per §9.
7. **Visibility mode and eligibility:** compute the maximum access level from §9.
8. **Billing check, only if the maximum level is L2 and L2 is billable** (not a connection, not an OD-08a exemption): a ProfileView grant for (billing account, target) must exist in the last 24 hours. If it doesn't: `402 profile_view_required` with the L1 card (OD-08b). **A grant never raises the level above step 7.**
9. Serialize with the allowlist for the computed level. `Cache-Control: private, no-store`.

**Consequences:**
- Pay, then get blocked → 404 at once.
- Pay, then the target switches to HIDDEN → 404 at once (no L3 between them).
- Pay, then the target restricts → denied.

In every case the used credit isn't refunded (REC-BIZ, OD-08c). The grant row stays as a billing record.

`POST /profiles/{id}/views/` runs steps 1–7 first. It **refuses to charge** when the maximum level is below L2, returning a generic `403 profile_detail_not_available`, which reveals nothing beyond the L1 card the viewer already has.

**Tests:**
- T-MAT-017: GET never charges.
- T-MAT-018: a grant never exceeds the computed level.
- T-MAT-019: block or hide after a grant → denied.
- T-MAT-020: visibility changed to HIDDEN after a grant → denied.
- T-MAT-021: POST refuses to charge when L2 isn't permitted.
- T-MAT-022: responses are never cached.

### 10.4 Refresh rotation: limits of replay detection and compromise response (C9)

The design is kept: deterministic HMAC derivation and a 15-second idempotent grace. Its limits:

**What it does not prevent:**
1. **A replay inside the grace window gets the same pair.** An attacker who presents a stolen parent within 15 s of its legitimate use receives the identical access and refresh tokens. Nothing is detected **until one side uses the child refresh token after the other**. Until then, the attacker's access token works for up to 15 minutes.
2. **A stolen, still-unused refresh token** can be used by the attacker first. Detection happens only when the legitimate client later presents it (reuse), so the attacker has a session until then.
3. **If the legitimate client never refreshes again** (uninstalled, device lost), the attacker's chain is never detected. It ends only at the 30-day idle or 90-day absolute limit, or when the user revokes sessions or resets their password.
4. Detection relies on reuse, so it's **after the fact**. It limits how long a compromise lasts. It doesn't stop theft.

The grace window is therefore **a deliberate trade-off that adds a small replay surface in exchange for recovering lost responses.** It doesn't eliminate replay risk.

**Mitigations:**
- Tokens only ever live in the platform's secure keystore (Expo SecureStore).
- TLS only.
- Tokens are never logged.
- Every session appears in the session list, so the user can revoke it.
- A new-sign-in security notice is sent.
- Optionally (behind a feature flag, off by default), a device-binding check that compares the platform and app identifier recorded at login.

**Response to suspected compromise:**

| Trigger | Action, in the same transaction |
|---|---|
| Refresh reuse detected | Session → REVOKED (`REFRESH_REUSE`). Every token in the session revoked. `AccountSecurityEvent REFRESH_REUSE_DETECTED`. Outbox security notification ("a sign-in was ended for your protection"). The response is `401 session_revoked`. |
| User reports compromise, or "sign out everywhere" | Revoke all sessions (`USER_REVOKED_ALL`). Recommend a password change. |
| Password reset | Revoke all sessions [v3]. Event. Notification. |
| Repeated reuse events on one account (≥ 2 in 24 h) | `SUSPICIOUS_ACTIVITY` event and an alert to the security admin role. No automatic lockout. |

**K_rot key management:**
- **Where it's used:** K_rot only derives child tokens. Verifying a token never needs it (the server hashes the presented token). The only time an old key is needed again is to recompute a pair during the 15-second grace replay.
- **Storage:** the deployment secret store, as versioned entries `K_rot[v]`. Never in Git, the database or logs. The active version is in configuration.
- **Planned rotation** (recommended every 90 days): add `v+1` and make it active, so new rotations use it. Keep `v` for at least 15 s plus a margin (1 hour), then retire it. **No sessions are revoked.** Tokens already issued stay valid because verification is hash-based.
- **Compromise of K_rot alone:** an attacker can't produce valid tokens without a parent token's plaintext, so the direct impact is limited. But it combines dangerously with any token theft, so the procedure is:
  1. Mark `K_rot[v]` as COMPROMISED in configuration. Rotation and grace replays refuse to use it, and a grace replay under v returns `401 session_expired`.
  2. Activate a new version.
  3. Run the management command `revoke_sessions_by_key_version v`. It revokes every ACTIVE mobile session whose `key_version_current = v` (reason `KEY_COMPROMISE`), writes the events, and queues notifications in batches.
  4. Open a security incident and record it in AuditLog.
  5. Review the HMAC fingerprint key and other secrets in the same store.
- **Web sessions aren't affected by K_rot.** If Django's `SECRET_KEY` is compromised, a separate procedure revokes all web sessions (rotate the key, flush the session store, bulk-revoke WEB AuthSessions).

| ACTIVE / PAUSED → CLOSED | Either party, moderation, deletion processing | With a reason |
| CLOSED → ACTIVE | Both parties confirm via `ConnectionReopenRequest` [DECIDED] | Not while a block exists |

**Effects:**
- ACTIVE = L3 + messaging.
- PAUSED / COMPLETED = L2 + read-only.
- CLOSED = §9.

### 11.7 Relationship progress (`RelationshipProgress.stage`)

Stages: REQUEST_ACCEPTED (initial), INITIAL_COMMUNICATION, DISCUSSION_IN_PROGRESS, MEETING_PLANNED, MEETING_COMPLETED, PROPOSAL_SERIOUS_DISCUSSION, ENGAGED.

Recommended rules (REC-BIZ, OD-06k):
- Any stage can move to any other stage, because real life isn't linear.
- Either participant (owner, or a manager with `manage_relationship_progress`) can update it, **only while the connection is ACTIVE**. The other party is notified.
- Every change writes history (previous, new, actor, represented profile, time) [DECIDED, FR-CON-005].
- The "Closed" label is derived (§7 B).

### 11.8 Conversation

There's **no stored status**. It's derived from the connection:
- ACTIVE: send and read
- PAUSED or COMPLETED: read only
- CLOSED: read only, per retention
- Block in either direction: no access

This satisfies doc 15 §8's rule that a conversation can't be more permissive than its connection, by construction.

### 11.9 AuthSession / AuthToken

AuthSession:
- ACTIVE → REVOKED (with a reason, §10.5)
- ACTIVE → EXPIRED (idle or absolute; enforced at runtime and swept by a job)

Both end states are terminal. AuthToken: issued → used, revoked or expired.

### 11.10 Subscription (manual renewal for the MVP, OD-09)

- PENDING_PAYMENT → ACTIVE (payment verified [DECIDED])
- PENDING_PAYMENT → CANCELLED
- ACTIVE → EXPIRED at `ends_at`
- ACTIVE → CANCELLED: stops future renewal; benefits continue to the period end [DECIDED, FR-SUB-009]

An early renewal creates a queued term that starts at `ends_at`. PAYMENT_FAILED and GRACE exist in the schema but stay **dormant** (FR-SUB-008) until auto-renewal is approved.

### 11.11 Credit allowance

- ACTIVE → EXHAUSTED (fully consumed)
- ACTIVE / EXHAUSTED → EXPIRED at the period end, writing the expiry ledger entry for any remainder [DECIDED]
- EXHAUSTED → ACTIVE only through a refund to that allowance before it expires (OD-07)

### 11.12 Account deletion

- REQUESTED → IDENTITY_VERIFICATION_REQUIRED → PENDING_RECOVERY (all sessions revoked, §10.6)
- PENDING_RECOVERY → CANCELLED (recovery session)
- PENDING_RECOVERY → PROCESSING at `recovery_ends_at` (job, under lock)
- PROCESSING → COMPLETED
- REJECTED (from verification failure or a legal hold)

COMPLETED can't be reversed [DECIDED].

### 11.13 Unchanged from doc 15

Payment, shared document permission, notification delivery, moderation case and data export: doc 15 §§9, 10, 12, 13 and 14, unchanged.

## 12. Global Lock-Order Policy (TR-09; DCR-42; ADR-031)

**Order.** Inside any transaction, locks are always acquired in this order. Skipping steps is allowed; going backwards is not.

| Step | Lock |
|---|---|
| 1 | **Authorization row:** `FOR SHARE` (delegated write) or `FOR UPDATE` (pause, revoke, resign) |
| 2 | **Account-scoped rows:** `AccountDeletionRequest`, then `User`, `FOR UPDATE`. Account-state changes only. |
| 3 | **Pair advisory locks:** `pg_advisory_xact_lock(NS_PAIR, key)`. If more than one, in ascending key order. |
| 4 | **Billing wallet:** `CreditWallet` `FOR UPDATE`. One per transaction; if ever two, in ascending account ID. |
| 5 | **Allowances:** `FOR UPDATE ORDER BY expires_at, id` |
| 6 | **Domain rows**, in type order Interest → MatrimonialRequest → ProfileConnection → ConversationMessage/document permission, each type by ascending ID |
| 7 | Inserts only: history, ledger, audit, outbox |

**Rules:**
- **Never take a pair lock after a wallet lock.** View billing takes step 4 without step 3, which is safe.
- Reads that control a pair-scoped write happen only after step 3.
- **Bulk jobs** (expiry, deletion processing, block side effects) handle **one aggregate per transaction** (one pair, one account) so their lock sets stay small.
- **No external calls** (SMS, payment gateway, storage) inside a locking transaction. Use the outbox.

**Deadlocks and retries:**
- Each transaction sets `lock_timeout = 5s` (configurable). PostgreSQL detects deadlocks (`deadlock_timeout` default).
- A `@retry_on_contention` decorator on service entry points retries the **whole transaction** on SQLSTATE 40P01 (deadlock), 40001 (serialization failure) and 55P03 (lock not available). It makes up to 3 attempts with jittered backoff (50–400 ms). If they all fail, it returns `503 temporarily_unavailable` with `Retry-After`.
- Retrying is safe because every side effect (ledger, outbox, history) is inside the transaction, and financial operations also carry idempotency keys.
- Each retry is logged with a metric.

**Interest-to-request conversion** (clarification 1):
1. Steps 1, 3 and 4–5 per the order above.
2. Load the live interest `FOR UPDATE`, applying lazy expiry if due.
3. Debit the credits.
4. Insert the `MatrimonialRequest` with `source_interest=interest`. The **OneToOne unique constraint** makes a second request from the same interest impossible even if the locking were bypassed.
5. Set the interest to CONVERTED_TO_REQUEST.
6. History, ledger, outbox.

A concurrent second conversion waits on the pair lock, then sees CONVERTED_TO_REQUEST and is rejected without charging. With an `Idempotency-Key`, a client retry replays the first response. Test T-INT-012: 10 concurrent conversions produce 1 request and 1 debit.

**Tests:** T-LOCK-001 (opposite-order operations don't deadlock), T-LOCK-002 (deadlock injection is retried and succeeds), T-LOCK-003 (retries exhausted return 503 with no partial effects).

## 13. Calendar and Time Rules (TR-04)

- All timestamps are `timestamptz`, stored in **UTC**.
- **Request expiry** = `sent_at + relativedelta(months=3)`, computed on the UTC timestamp with the time of day kept and the date clamped at month end:
  - 2026-11-30 10:00Z → 2027-02-28 10:00Z
  - 2027-11-30 → 2028-02-29 (leap year)
  - 2026-08-31 → 2026-11-30
  - 2026-01-15 → 2026-04-15
- "**30 days**" (cooldowns, deletion recovery) = 30×24 hours. "**24 hours**" (view window) is rolling.
- Clients show times in the user's timezone.
- **AS-7:** the calendar month is counted from the UTC date. For a request sent between 00:00 and 05:00 PKT, the UTC date is the previous day, so the expiry date can appear one calendar day earlier in local terms. If you prefer Pakistan local-calendar semantics, the computation changes to the user's timezone, still stored in UTC.
