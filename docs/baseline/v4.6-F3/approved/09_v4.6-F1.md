## Correction 1: removing the circular hash in the maintenance log

**Affected:** v4.6-F §A.1 (the `log_rows` field and the "local log mirrors chain" note) and v4.5 §5.3. **DCR-95. Contradiction C-66.**

**The problem:** v4.6-F put complete log rows, including their `entry_hash`, inside the registry entry, and the entry's own hash covered those rows. So the hash depended on itself.

### Revised specification text (replaces v4.6-F §A.1)

> **A.1 Registry entry structure.** Every registry entry has four parts: `header`, `params`, `entry_hash` and `signature`.
>
> **Header** (non-derived, no personal data). One registry entry corresponds to **exactly one** `maintenance_audit_log` row. The header *is* that row's recoverable content:
> `schema_version`, `stream`, `seq`, `prev_hash`, `registry_key_version`, `op_id`, `parent_op_id`, `kind`, `phase`, `log_row_id` (UUIDv7, generated before seq allocation), `target_digest`, `params_digest`, `companion_ref` (`{key, sha256, count}` or null), `summary` (an operational object: table, partition name, range bounds, counts, digests; **never pseudonyms**), `executor_job_run_id`, `executor_role`, `requested_by_pseudonym`, `approvals` (array, Correction 5), `recorded_at`.
>
> **Params:** the kind-specific recoverable parameters (A.3, Correction 3). Bound to the header by `params_digest = SHA-256(JCS(params))`.
>
> **Canonical hash input:** `H_in = "MATREG" ‖ 0x00 ‖ "v1" ‖ 0x00 ‖ JCS(header)`, where JCS is the RFC 8785 JSON Canonicalization Scheme in UTF-8. Encoding rules:
> - UUIDs: lowercase.
> - Timestamps: RFC 3339 UTC with milliseconds and a `Z`.
> - Digests: lowercase hex.
> - Integers: JSON numbers below 2^53, otherwise decimal strings.
> - Absent optional fields: explicit `null`.
>
> **Hash and signature:** `entry_hash = SHA-256(H_in)` and `signature = HMAC-SHA256(K_reg[registry_key_version], entry_hash)`.
>
> `entry_hash` and `signature` are **not** part of `H_in`. `seq` and `prev_hash` **are** part of it, which is what links the chain. So there's no circular dependency.
>
> **Local log row:** `maintenance_audit_log` columns = every header field, plus `entry_hash` and `restored_from_registry`. `params` aren't stored locally, which keeps Stream R pseudonyms out of the long-lived local log.
>
> **Reconstruction procedure:**
> 1. Fetch the entry.
> 2. Verify `signature` over `entry_hash`.
> 3. Recompute `SHA-256(H_in)` from the header and require it to equal `entry_hash`.
> 4. Require `prev_hash` = the previous entry's `entry_hash`, and `seq` = previous `seq` + 1.
> 5. Recompute `params_digest` and require a match.
> 6. Insert the local row from the header fields, with `seq`, `prev_hash` and `entry_hash` copied from the verified entry, using `ON CONFLICT (id) DO NOTHING` and `restored_from_registry = true`.
>
> **Local verification:** from local columns alone, rebuild the header, recompute `entry_hash`, and check the chain across rows ordered by (`stream`, `seq`).

**Test T-REG-036:** with an empty `maintenance_audit_log`:
- reconstruct every row from registry entries
- recompute every `entry_hash` **from local columns only** and confirm each matches
- verify the chain is continuous
- change any local column, or any `params` byte → detected
- confirm the hash is computed **before** the local row exists, which shows there's no circular dependency

## Correction 2: making PARTITION_DROP fully recoverable

**Affected:** v4.6-F §A.3 (the PARTITION_DROP row) and T-REG-030 / 032. **DCR-96. Contradiction C-67.**

### Revised specification text

> **Companion for PARTITION_DROP:** a canonical JSON Lines object, UTF-8, `\n`-terminated:
> - **Line 1 (header):** `{"format":"matreg-companion-v1","op_id":…,"kind":"PARTITION_DROP","table":…,"partition_name":…,"event_count":n,"link_count":m}`
> - **Then one line per held event**, sorted by `id`: `{"t":"event","row":{…every column of the audit_log row exactly as stored…}}`. This includes the plaintext event facts, the pseudonyms and `enc_parts` (ciphertext). These are the same pseudonymous or encrypted values the log already holds, and **no direct identifiers** (v4.5 §2.3–2.4).
> - **Then one line per hold link**, sorted by (`event_id`, `hold_case_id`): `{"t":"link","event_id":…,"hold_case_id":…}`
>
> `companion_ref.sha256` = SHA-256 of the whole object. It's in the header, so it's protected by `entry_hash` and the signature.
>
> **Companion retention:** object lock = the longest backup retention + 30 days. The companion only matters for restoring from a backup taken before the drop, and every later backup already contains `audit_log_hold`.
>
> **Reconstruction on restore:**
> 1. Fetch the companion and verify its digest and line counts.
> 2. In one transaction, insert every event row into `audit_log_hold` and every link into `audit_log_hold_link`, both with `ON CONFLICT DO NOTHING`.
> 3. If the restored partition contains a held event, its stored row must be byte-equal (in canonical JSON) to the companion row. If it isn't → integrity alarm.
> 4. DETACH and DROP the partition if present.
> 5. Verify: every companion event and link is present, and the partition is absent.
>
> Rows inserted into that partition after the backup and **not** held are legitimately gone, because their retention had ended. That difference is recorded as `RESTORE_DIVERGENCE` and doesn't count as a failure.
>
> **Missing or altered companion:** integrity alarm. The operation goes to `BLOCKED_OPERATOR`, and **the partition isn't dropped**, because it may be the only remaining copy of held data. Stream M doesn't halt. The operator recovers the companion from a replica or a previous object version, then records an `OPERATOR_INTERVENTION RESUME`.
>
> **The held set changes between INTENT and apply** (a new hold or a release): the apply transaction rolls back, the operation is `ABORTED` (proven not applied), and the drop is planned again.

**Tests:**
- **T-REG-037:** restore a backup **taken before the drop** that's missing held rows inserted after the backup → every held record and link is rebuilt from the companion, the partition is dropped, `RESTORE_DIVERGENCE` is reported for the non-held difference.
- **T-REG-038:** companion missing → `BLOCKED_OPERATOR`, partition kept, alarm raised.
- **T-REG-039:** companion altered (digest or line count mismatch) → same as T-REG-038.
- **T-REG-040:** held set changes between INTENT and apply → ABORTED, then planned again.
- **T-REG-032** (amended): now refers to T-REG-038 / 039.

## Correction 3: Stream R parameter schemas

**Affected:** v4.6-F §A.3, §B.1, §B.4. **DCR-97. Contradiction C-68.**

### Revised specification text (added to §A.3; Stream R)

> **`DELETION_INTENT` params:**
> - `account_pseudonym`
> - `profile_pseudonyms` (array; at most one personal profile per account [DECIDED])
> - `expected_shred_subjects`: array of `{pseudonym, subject_type: ACCOUNT|PROFILE}`
> - `recovery_ends_at` (UTC)
> - `requested_on` (date only)
> - `identity_confirmed: true`
> - `holds_active_at_intent` (count)
> - `deletion_step_plan_version` (the catalogue version of idempotent deletion steps)
> - `reason: "USER_REQUEST"`
>
> The header has `parent_op_id = null` and `target_digest = SHA-256(account_pseudonym)`.
>
> **`SHRED_INTENT` params:**
> - `pseudonym`, `subject_type`
> - `key_ids` (array of `SubjectDataKey.key_id`, which are random and opaque)
> - `kek_versions` (array)
> - `actions: ["DESTROY_KEYS","UNLINK_PSEUDONYM","CACHE_INSERT"]`
> - `holds_active_at_intent` (count)
>
> The header has `parent_op_id` = the deletion operation's `op_id` and `target_digest = SHA-256(pseudonym)`.
>
> **`DELETION_COMPLETED` / `SHRED_COMPLETED` params:** `{ "completed_steps": [...], "children_completed": [op_ids] }` / `{ "destroyed_key_ids": [...], "not_present_key_ids": [...] }`.
>
> Stream R params contain only pseudonyms, opaque key IDs and operational values. No other identifiers. That's consistent with v4.6 §2.1 and v4.6-F §A.2, where opaque key IDs are now explicitly listed as allowed in R.
>
> **Recovery rules when the database operation rows are missing (restore):**
> 1. Process Stream R in `seq` order. A child's INTENT is always written after its parent's INTENT, so a parent is rebuilt before its children.
> 2. Rebuild the parent operation from `DELETION_INTENT` (same `op_id`, state `INTENT_REGISTERED`, step markers empty) and run every step of `deletion_step_plan_version` idempotently (B.2 steps 4–11, including the `RESTORE_REAPPLY` path).
> 3. Rebuild each child from `SHRED_INTENT`. **Required:** the parent exists, and the child's `pseudonym` is in the parent's `expected_shred_subjects`. Otherwise → integrity alarm, and the child goes to `BLOCKED_OPERATOR`.
> 4. A `key_id` not present in the restored database is recorded in `not_present_key_ids`, with no failure.
> 5. If the matching `*_COMPLETED` entry already exists, the operation is marked COMPLETED locally without writing a second entry (v4.6-F B.4).

**Tests:**
- **T-REG-041:** deletion operation rows missing (backup from before the deletion request) → rebuilt from `DELETION_INTENT`, all steps re-run, COMPLETED.
- **T-REG-042:** shred operation rows missing → rebuilt from `SHRED_INTENT` after its parent, keys destroyed, COMPLETED.
- **T-REG-043:** a child pseudonym not in the parent's `expected_shred_subjects` → alarm, `BLOCKED_OPERATOR`.
- **T-REG-044:** a `key_id` missing from the restored database → recorded as not present, operation completes.

## Correction 4: protecting financial events when a queue key is destroyed

**Affected:** v4.6 §1.1–1.3 (outbox), v4.6-F §A.3 (QUEUE_KEY_DESTROY), v4.3 §2.1 (the refund obligation). **DCR-98. Contradiction C-69.**

### Revised specification text

> **Event classes:** OutboxEvent gains `event_class`, either **NOTIFICATION** or **FINANCIAL_OBLIGATION** (currently just `REQUEST_REFUND_DUE`).
>
> **A financial event is a wake-up signal, never the record of the obligation.** Every financial event type must be **re-derivable from authoritative domain records**. For refunds: a `MatrimonialRequest` that is CANCELLED with a refundable reason (OD-07) and has no `CreditRefundOperation` is an outstanding obligation. The nightly reconciliation already checks this (v4.4 §3.4), and now also re-creates the trigger.
>
> **Retention:**
> - A FINANCIAL_OBLIGATION event in `PENDING`, `CLAIMED`, `DEAD` or `BLOCKED_INTEGRITY` is never redacted or purged.
> - It's redacted 7 days after `DONE`, and `DONE` is set only after the refund passes verification (v4.5 §3).
>
> **QUEUE_KEY_DESTROY precondition** (replaces v4.6-F): the INTENT is refused unless all of these are zero:
> - (a) NOTIFICATION rows using the version that are non-terminal or unredacted
> - (b) FINANCIAL_OBLIGATION rows using the version in any status other than redacted `DONE`
> - (c) outstanding refund obligations from the reconciliation check
>
> **Restore when the queue-key version is already destroyed:**
> - **Undecryptable NOTIFICATION events** → `CANCELLED (KEY_DESTROYED)`. They're stale notifications from before the backup.
> - **Undecryptable FINANCIAL_OBLIGATION events** → the new terminal status `DEAD_UNDECRYPTABLE`, with `dedupe_key` redacted (a value → NULL transition is allowed on terminal rows).
> - Then **financial obligation re-derivation** runs as a mandatory restore step **before the startup gate opens**: every outstanding obligation gets a new event encrypted with the current queue key.
> - The startup gate needs zero outstanding obligations without a live event.
> - Doing the refund exactly once is still guaranteed by `refund:request:<id>` (v4.4 §2).
>
> The redaction trigger's terminal set becomes `{DONE, CANCELLED, DEAD, DEAD_UNDECRYPTABLE}`. `DEAD` financial events are excluded from redaction until an operator resolves them.

**Tests:**
- **T-OUT-007:** restore an older backup containing a PENDING refund event whose queue-key version has since been destroyed → `DEAD_UNDECRYPTABLE`, the obligation is re-derived, the refund completes exactly once, the startup gate opens only after that.
- **T-OUT-008:** a QUEUE_KEY_DESTROY INTENT is refused while any non-redacted financial event, or any outstanding obligation, uses the version.
- **T-OUT-009:** an undecryptable notification → CANCELLED.
- **T-OUT-010:** a qualifying CANCELLED request with no refund and no live event → reconciliation re-creates the event.
- **T-OUT-011:** a crash during re-derivation, then a rerun → no duplicate event (dedupe) and no duplicate refund.
- **T-OUT-012:** `DEAD` financial events aren't redacted or purged by retention.

## Smaller consistency corrections (DCR-99)

### 5. Two distinct approvers for OPERATOR_INTERVENTION (C-70)

> **Header field `approvals`:** an array of exactly two entries, `{approver_pseudonym, approved_at, approval_ref}`.
>
> **Database:** table `maintenance_approval (op_id, approver_user_id, approved_at, permission_code)` with:
> - `PRIMARY KEY (op_id, approver_user_id)`
> - a CHECK trigger ensuring the approver isn't the `requested_by` account
>
> **Service rule:** RESUME or ABORT_WITH_EVIDENCE needs **two rows from distinct staff accounts**, each holding `maintenance.approve_intervention` at approval time (checked against the single admin-authorization source, TR-07), and neither may be the requester.
>
> **Registry:** both approver pseudonyms and timestamps appear in the header.

**Test T-REG-045:**
- the same approver twice → rejected
- the requester as an approver → rejected
- an approver without the permission → rejected
- two valid approvers → accepted, with both shown in the entry

### 6. Order for writing companion objects (C-71)

> Applies to every operation with a companion (PARTITION_DROP, HOLD_RELEASE, RESTORE_RECONCILE):
> 1. Build the companion and compute its SHA-256.
> 2. Conditionally create it at the **content-addressed** key `M/companions/<op_id>/<sha256>.jsonl` with object lock. This replaces v4.6-F's `<stream>/<seq>.c`, because the `seq` isn't known yet at this point.
> 3. Read it back and verify the digest.
> 4. Only then allocate the `seq` and write the INTENT entry with `companion_ref`.
>
> A crash after step 2 leaves an unreferenced companion. That's harmless: it's reported by the nightly check and expires with its retention.
>
> An INTENT is never written that points to a companion not yet confirmed.

**Test T-REG-046:**
- a crash after the companion put but before the INTENT → orphan reported, no INTENT, retry succeeds
- an INTENT can't be written before read-back verification succeeds

### 7. Checking retention before HOLD_RELEASE deletes anything (C-72)

> **HOLD_RELEASE apply,** per candidate event in `released_event_ids`:
> - (a) after removing this hold's links, **no active hold link remains**
> - (b) the event's pseudonyms aren't under any other active hold
> - (c) `occurred_at + retention(category) ≤ now`, using the **stricter** of the retention values in force at INTENT time and at apply time
>
> Only events meeting all three are deleted. Events that fail (c) stay in `audit_log_hold` with no link and `retain_until` set.
>
> **New M kind `HOLD_RETENTION_PURGE`:**
> - params: `event_ids` (companion), `evaluated_at`
> - re-apply: the same three checks, then delete
>
> On re-apply after a restore, the checks are evaluated again, and the deleted set must be a subset of the listed IDs.

**Test T-REG-047:**
- an event still under another hold → kept
- retention not yet reached → kept with `retain_until`, removed later by `HOLD_RETENTION_PURGE`
- re-apply on restore deletes no row outside the recorded list

### 8. Restoring a PARTITION_CREATE that was later dropped (C-73)

> During restore, Stream M is processed in `seq` order with an intended-state rule for each (`table`, `range`):
> - **A later PARTITION_DROP exists for the range (COMPLETED, or in flight with a verified companion):** CREATE is **skipped**, and the drop is re-applied per Correction 2. If the partition is missing from the restored database, only the held records are rebuilt.
> - **CREATE is COMPLETED and no drop exists:** the partition is created if missing. This is the **only** allowed exception to the "never create a past range" rule (v4.5 §5.1), and it's recorded in RESTORE_RECONCILE.
> - **CREATE is in flight with no COMPLETED:** it's re-applied normally.

**Test T-REG-048:**
- (a) backup from before the create → partition stays absent, held records rebuilt
- (b) backup taken between create and drop → drop re-applied
- (c) drop in flight → completed from the companion
- (d) a create with no later drop on a past range → created, exception recorded
